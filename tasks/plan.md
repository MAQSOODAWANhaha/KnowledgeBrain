## 目标与边界

每一条已知要求及已安排的技术响应行都可追踪到检索、实际采用内容、复核或明确待补出口。
没有知识依据时企业应答留空；人工报价、原格式、原要求和适用条件完整保留。
文件技术导出成功与业务内容是否齐备分别展示，业务缺口不阻断生成、保存或下载。

复用现有分析五节点、编制执行、CAS、PG回执、epoch围栏及一次改稿；不引入自由Agent、
新调度系统、七套数据库状态、新环境变量或语义正则。保持当前模型、预算算法和并发配置。
本方案不解决所有文档业务问题，BUG-069的真实层级问题及共享Key限流须继续独立跟踪。

## 运行顺序与职责

`固定分析快照 → 组织/固定大纲 → 要求与响应行底账 → 固定查询计划 → 检索 → 选材 → 共同依据 → 分单元编写 → 既有复核 → 最多一次改稿/再核 → 宿主覆盖结算 → Word/ZIP`

- 模型：理解要求、组织用途、判断知识与应答的相关性及充分性、编写有据内容、复核。
- 宿主：固定身份/版本、建立显式关系、补齐缺失查询、执行检索、管理依据与引用、
  保存阶段产物、累计重试、结算覆盖及渲染文件。
- 人工：填写报价及未提供的企业事实、处理明确未决项、审定最终提交稿。

### 1. 按要求建立检索计划，漏意图只补一次

1. 从当前有效规则及已有`response_table.rows`建立响应底账，不从普通段落推断新要求。
   同一目标关联R1/R2必须分别检查；同一规则涉及不同主体/响应位置时分别记账。
2. 人工填写、仅允许招标原文支持的位置，以及已有明确约束/外部提交/不适用处置的要求，
   不强制知识检索。不能按事项类别或关键词推断所有评分条款都应搜库。
3. 没有细粒度响应行时，本条规则有明确`rule_ref`绑定的意图，才计为本条已有计划。
   已有响应行则按最细行的精确来源核对，不能以本rule的笼统摘要、同目标另一条规则、
   宽泛来源相交或章节标题替代。意图缺少可确认的行级关联时，仍由宿主按该行原文补查。
4. 对需要知识应答但缺少本条意图的底账，用固定的当前有效要求文本补查一次。
   没有正式规则的已知响应行，可用已有精确原文及共同条件生成同类宿主查询；
   不让模型另编问句。已有不同技术内容的多行分别用其完整原文查询；不能因同rule就
   强行共享摘要查询。只有实际query原值及范围相同，或固定输入明确包含全部对应行及
   条件时才共享，再绑定各自位置；同原文的多主体实例可以去重。
5. 查询文本保留原值。有效要求`text`属于上游分析文本，不一定是逐字引文，必须记录
   查询来源；不能把未经当前补遗投影的旧条款当作现行要求。没有可读文本则记
   `knowledge_query_missing`，不能仅用purpose或标题假装查询。
6. 模型意图仍限256字符；宿主原文查询走独立内部类型。当前项目知识入口上限是
   **20000 UTF-8字节**。超过时记`knowledge_query_too_large`并保留完整要求，
   不静默截断、不偷偷拆成多次查询。该出口是待补，不是生成失败。
7. 去重键包含查询原值、固定知识范围/版本、是否需要原件；多target只影响回绑，
   不引起相同检索重复发送。已有明确意图的查询失败只走原查询重试；成功空结果
   不触发第二种问法。写作复核后也不自动再次检索。

成功空结果保留`knowledge_no_hits`，配置缺失、服务失败、非法命中、越权/跨版本、
原件缺失分别保留真实码。无命中只表示本次未取到资料，不证明库中确无资料。
长中文全文查询的关键词分支可能低召回，须通过真实索引验收，不靠删掉条件解决。

### 2. 候选组织与检索后用途

- 全部合法命中先冻结，补存实际query、rank及可用score；同片段的多位置关系继续合并。
  不增加词汇重叠阈值，不把缺少词面交集的同义资料硬删。
- 按本单元涉及的要求分配候选，精确去重；容量不足时按各查询原排名轮流装入完整片段，
  避免一个要求的多条命中挤掉另一要求的唯一依据。不同查询的分数未经校准不直接比较。
- 不设未经验证的统一top-3等门槛。超大单片段不能截到丢条件；继续既有任务分片或记
  `knowledge_candidates_not_loaded`。落选仍保存在CAS，不得记成`knowledge_no_hits`。
- 大纲purpose描述待响应职责，不在无资料时承诺具体企业能力/技术路线。检索后由宿主
  附资料可用状态、待补原因，正文只使用实际资料；本批不增加“再生成purpose”调用。
  保留固定target_id、原模板、分册及要求，不因知识库缺资料删章节或降要求。

### 3. 在现有正文复核中补语义判定，宿主结算覆盖

仅凭`target_ids`、非空内容或有效`material_ids`不能证明逐要求满足。
保留现有block/cell/row/attachment写作返回形状，扩展正文R/R2的`assessments`：

```json
{
  "findings": [],
  "assessments": [{
    "coverage_id": "c3",
    "content_refs": [{"task_id": "w1", "content_ids": ["b1", "r2"]}],
    "result": "supported",
    "detail": ""
  }]
}
```

- `c3`为宿主提供的本请求短引用，绑定具体规则、响应位置及必要的响应行。
  跨单元联证可在同一assessment选择多个task的内容，避免不同单元的`b1`混淆。
- 模型只选择实际判断的对象与内容、给充分/部分/不支持结论；不重抄完整覆盖表、
  原文、知识清单、CAS或版本哈希。结构核对F不要求返回正文assessments。
- 宿主校验对象在本批、内容实际存在且非空、允许来源/目标/版本绑定均合法，
  再绑定受审unit_ref。知识依据可追溯与R语义充分判定必须同时成立。
- 宿主预先记录本批是否包含该覆盖项的完整相关应答范围。局部supported或多个partial
  不自动合为完整覆盖。能在既有R批次完整共读则共读；放不下则保留部分/未核及范围缺口，
  不新增自动联合复核回合。
- 未返回assessment、旧回包无该字段、局部坏引用均保留明确未核状态，不能整篇拒收。
  `partial/unsupported`只表示要求尚未满足；内容删除仍按已有`findings.reject_content`，
  不能误删正确但不充分的段落。
- 改稿后只认实际采用版本对应的R2，旧稿判定不得平移。R2失败沿现有安全稿采用策略，
  若原稿已被明确否定不能复活。删块改变unit_ref时未重新核对的判定降为未核，
  不添加复杂的跨版本推测映射。

覆盖底账包括：全部有效规则、其显式响应位置、已知业务响应行（无rule也不能漏），
以及已有约束/提交/不适用处置。按显式关系生成，不能做所有规则×所有章节的笛卡尔积。
同规则对应多行时逐行留账，规则汇总不能因某一行已填而全部完成。
未知处置、未落位置、条件未决继续待核，不新增`mandatory`关键词分类。

结算只读取实际最终采用清单。每项记录原要求/位置、查询与候选、采用内容、依据、
语义判定、复核状态和真实缺口；正文有据但review不可用时保留正文且标未核。
人工填写表示已安排人工出口，不表示已经填写；提交待办不表示已经签章/上传。
技术执行仍可`SUCCEEDED`，页面显示“草稿已生成，X项待补、Y项待核”，
不得仅因导出成功显示“全部要求已完成”。覆盖表进交付包/问题侧栏，不插进每章正文。

### 4. 用现有回执补阶段检查点

| 检查点 | 最少保存的持久引用与依赖 | 恢复行为 |
| --- | --- | --- |
| outline | 输入身份、固定大纲、要求底账 | 普通同执行恢复直接采用固定版本，不重新组织 |
| retrieve | 查询计划、逐操作尝试、查询结果、候选选择 | 已持久提交的成功/空结果不重查；继续未完成操作 |
| basis | 选材、共同依据及其输入摘要 | 直接读取完整已接受依据 |
| write | 稳定任务清单、逐单元unit_ref与输入摘要 | 每个单元完成立即保存；不等整个gather结束 |
| review | 批次、受审unit_ref、findings/assessments | 只核未完成批次；不复用不同版本判定 |
| revise/adopt | 一次改稿、再核、最终安全采用清单 | 改稿次数跨恢复不重置；不把未核改稿当已采纳 |
| export | 最终采用清单、coverage_ref、渲染版本、文件引用 | 渲染失败仅重导出；已有文件先校验引用 |

这些是一个编制执行内部的持久产物，不是七个新业务主状态。复用`receipt/commit_artifact`
与epoch围栏，不新建表或通用工作流。模型成功回执已存、unit_ref未提交时，恢复重验回包
并提交单元，不重新发送。同执行输入固定；修改要求/资料建立显式后继执行，不原地改身份。

知识HTTP操作在发送前持久登记尝试序号，收到结果后另存不可变结果回执，持久提交后才返回；
崩溃后的未知尝试也消耗首次加三次额度。远端成功但本地结果未提交仍属未知，不保证跨网络
exactly-once。只保留一层重试控制，不能外层4次×provider内层4次。证明元数据和原件
下载也按各自固定操作身份累计，失租worker不得写新采用结果。正常空命中不是失败重试。
不改变LLM的sent/uncertain、成功回执及付费围栏，不清缓存或给请求加盐。

## 调用量、请求容量和修订成本

设Q0为原去重意图数，E为需要补查的不同要求/源文行原值数，M为所选资料范围/版本数。
实际固定范围查询数Q满足`Q ≤ M × (Q0 + E)`，相同原值进一步去重。
查询HTTP发送至多`4Q`；证明元数据D次、原件下载K次另计，总相关HTTP上界为
`4(Q + D + K)`。当前F3已实现上述持久尝试与单层重试；旧knowledge-attempt聚合回执
无法证明各scope及metadata/file的历史操作次数，不追认为满足此界。旧记录保持不可变，
跨合同修复建立显式后继执行。
知识服务内部Embedding/其他模型费用单独记录，未知用量不当作免费。

编制LLM逻辑调用`L = O + B + W + V + C + V2`：O为现有来源/组装/结构核对及其已有一次
结构修订，B为依据批次，W为实际写作请求，V/V2为实际正文初核/再核批次，C为定向改稿。
沿现有同逻辑操作首次加三次额度，发送上界`4L`；成功回放减少实际发送。
不新增检索决策模型或第二轮检索，不产生全章节/全事项两两调用。
覆盖结算与检查点新增模型调用为0；assessments会增加V/V2的输出和必要分包，不能称费用零增长。
增长由实际响应实例、支持片段及批次决定，不能仅按页数保证固定包数。

单请求输入为`Prompt/Schema + 本批要求及条件 + 模板 + 去重知识 + 实际内容/反馈 + 短引用映射`。
输出为实际正文/填值或`findings + assessments`；后者量级为`O(本批覆盖项数 + 内容引用数)`。
分包同时计入新增Schema/映射/输出负荷，不能只按输入 fits 合批。必要条件与实际证据不得为了
压缩丢失。当前输出预留不是供应商API硬上限，巨型条款/单元也没有已验证的固定最坏输出值；
实施须测最大真实请求与回包，并沿现有分片、局部缺口及重试出口，不悄悄改算法或配置。

同执行中断：只补未完成HTTP操作/单元/复核/渲染；已接受成功调用新增发送为0。
人工通过既有结构化输入补一个字段且不请求AI时只重组装/结算/导出。直接编辑Word则
沿原DOCX保存及版本链，相关覆盖标未知/待核，不能用旧unit_refs重渲染覆盖人工稿。
显式后继执行变更一个要求或资料时，
只失效其真实依赖的查询、依据、写作和复核；共享依据改变可能影响多章，须先报告实际数量。
覆盖结算本身始终可由最终采用引用重算，不需重读全源。协议升级改变的完整请求摘要不保证
复用旧回包，不重写旧执行、人工Word或分析/确认结果。

## 验收矩阵

| 编号 | 输入/故障 | 必须看到的结果 |
| --- | --- | --- |
| A1 | 同target两规则，只有R1意图 | R2原要求补查一次；不能因R1掩盖漏查 |
| A2 | 同原文两个主体；同rule两行不同技术内容；另有无rule行 | 仅同原值查询共享；不同原文行分别查，不能被摘要掩盖；各主体/行分别结算 |
| A3 | 超256字符但不超20000字节的要求；另有超限条款 | 前者原值发送；后者明确超限待补，完整原要求仍导出 |
| A4 | 空命中已持久提交，或第2次HTTP后kill | 已提交空结果恢复零重查；未提交结果按未知计额度，同操作总发送至多4次 |
| A5 | 配置缺失/超时耗尽/非法命中/跨版本/缺原件 | 各有真实码，不能一律no_hits；有效兄弟保留，草稿照常导出 |
| A6 | 低词面重叠的有效资料；两规则各有唯一依据 | 不因词重叠删有效资料；预算选材不让一条要求吞掉另一条候选 |
| A7 | 一target两规则只答一条；合成夹具里多行只答1行 | 其余行不算已响应，全部原要求与条件仍在Word。这里的行数不是106页文件的31行 |
| A8 | 合法引用但答非所问；正确的部分应答 | R不能判完整；部分正文不因partial/unsupported自动被删 |
| A9 | 跨unit多处局部应答，或R分到不同批 | 多个partial/局部supported不被宿主拼成全量完成 |
| A10 | R不可用、漏assessment、坏内容引用、旧回包 | 保留安全正文，逐项未核；不整篇拒收、不冒认已复核 |
| A11 | 人工报价、源文背景、评分约束、提交待办、有据排除 | 使用各自已有语义出口；报价留空，不强制全都知识应答或伪称人工已办 |
| A12 | 一个unit完成后kill；成功回包后unit提交前kill | 已保存unit不重写；后者重验回包绑定，零重复付费发送 |
| A13 | R完成后采用前kill；改稿后R2失败；过期worker提交 | 恢复采用同版安全结果；旧否定稿不复活；失租提交被围栏拒绝 |
| A14 | 导出前/中kill；随后只改一个要求/资料 | 导出恢复不重叫模型；变更仅重跑实际依赖并报告范围 |
| A15 | 固定纲、模板、分册、当前人工Word、旧分析/确认/回执 | 身份及原文保全；不覆盖人工Word，不改旧运行或成功回执 |
| A16 | 技术导出成功但还有缺口；旧文档无覆盖表 | 显示草稿及待补/待核；旧文档显示覆盖未知，不能追认为完整 |

### 分三层验收，不能相互替代

1. **隔离技术回归**：先让A1/A7/A12等反例在旧实现失败，再实现修复；覆盖纯函数、现有
   文档执行、真实隔离PG/Redis/CAS的中断恢复。定向通过后跑受影响完整Python回归；涉及
   新返回字段时核对Schema生成/Prompt，涉及页面展示时补API及浏览器验证。单测不算模型语义验收。
2. **真实106页文件、无企业资料**：完整跑分析输入到编制/Word/ZIP（若复用固定分析则明确标注），
   验证已有31行还在，未进表原文出现在待核区而不是被塞进旧表，14行表只保留自己已绑定的条件，已识别页首只有显式排除才消失，企业应答与报价留空、每项有明确出口、
   缺口不阻断。抽查Word实物，不能只看JSON或文件存在。覆盖表不得污染正文。
3. **真实检索纵切再全文件**：先选技术要求、评分证明、跨章节条件及人工价格一组，

### F3：一个窄操作执行器管理真实HTTP尝试

已实现并完成真Web适配器物理发送计数、故障窗口及隔离PG持久回执定向验证。
这证明操作额度和恢复合同，不证明知识检索语义召回或企业资料匹配质量。

只在知识适配边界复用现有store/lease，提供`run_operation(kind,key,send_once)`回调。
它是三类知识HTTP共用的小执行器，不是新Agent、调度器或工作流。职责为：

| 层 | 职责 |
| --- | --- |
| _FrozenKnowledge及持久runner | 单操作身份、独立start/outcome回执、跨恢复首次加三次、已提交成功/空结果复用 |
| WebKnowledgeProvider | 按固定selection调用对应provider并转传runner，聚合合法兄弟结果；不重试聚合全集 |
| KnowledgeProvider | 组HTTP、解析/验证search、document metadata和原件；不再内层range(4) |
| send_once | 一次物理业务发送及验证；返回可持久JSON或原件落CAS后的ArtifactRef，不保存Response/流 |

单独直接使用provider可用同一接口的内存runner；生产必须注入持久runner，不能靠
inspect.signature失败后回退到旧四次路径。搜索、元数据和文件分别按具体scope+实际参数
生成操作身份；search身份不包含include_original，取证明模式只补metadata/file。
不要把认证token写进key、回执或spec。网络/解析失败沿同一操作计数，耗尽后保留明确
缺口；崩溃后未知started也计次数，失租不能提交新结果。

多scope中A成功、B失败时，A只搜一次，B独立最多四次；聚合有materials不能让B停止重试。
同文件被多个query命中时metadata/file可共享成功结果；原件失败仍保留已取得文字。
不重试成功空命中，不因为文件下载失败重查成功search。

**不可变回执和发送权**：同一operation的第n次尝试使用两个确定性scope，分别为
`kind:key:attempt:n:start`和`kind:key:attempt:n:outcome`，共用`stage=knowledge-operation`；
不将start原地更新成outcome，也不修改store的不可变约束。额度只数start，发HTTP前必须
成功提交start；已验证成功/空结果须在outcome提交后才返回。恢复先读成功outcome，即使
knowledge-snapshot聚合回执尚未保存也不重发该操作。字段形态见字典。

同内容幂等提交不代表独占发送权。同执行的runner按operation使用局部asyncio.Lock合并；
进入锁后重读已存结果与额度，再登记/发送。进程接管仍由现有lease/epoch管理，不增加
分布式锁。取消、失租及持久存储异常原样退出，不被转成knowledge_unavailable后继续发HTTP；
仅知识HTTP/响应解析失败走这四次业务尝试，耗尽后沿现有待补出口保留安全草稿。

**故障窗口**：start已提交但未发送，或远端成功但outcome未提交，本地均只能判unknown；
该次消耗额度，恢复可在剩余额度内重试。已提交成功/空outcome后、聚合快照前中断则
恢复零重发。此合同保证累计最多四次尝试，不承诺跨网络exactly-once，也不改变LLM原有
sent/uncertain付费围栏。

旧执行只有聚合knowledge-attempt或knowledge-snapshot时，保留其原始证据，不猜测或
补写各scope/document/file的历史尝试。新单操作合同在显式后继执行生效，不通过修改旧
回执或清空失败记录来获得额外额度。

### F4：修正覆盖对象、版本和采用引用

已实现并完成查询/覆盖修订定向验证；宿主元数据使用正式类型持久保存，避免序列化

**先补底账**：有response_table.rows时照常建立行级条目；对
`target.rule_refs − union(row.rule_refs)`中的每条共同规则，另建

```json
{
  "coverage_id": "c1",
  "refs": [{"task_id": "w1", "target_id": "t1", "rule_ids": ["R1"], "row_id": "q1"}],
  "scope": "complete"
}
```

规则全文、主体、位置仍放已有units视图，不重复发送。related任务按正式rule/target/row

该cN允许范围，局部非法仅丢该项并记诊断，保留兄弟判定和原正文。

**形态统一**：复用一个薄的内容索引/存在性helper，识别实际bN/fN/rN/aN。段落看text，

采用稿中有真实material_id/artifact_ref，不能只凭标题。输入、接收、最终结算不能各有
一套仅text检查。模型仍负责相关性、充分性及所需条件的语义判断。

**最终采用**：先按最终单元版本筛判定，再选择实际有效轮次/范围，最后从有效判定的

不能直接冒称完全未填写，也不能据此授予覆盖。

同最终版本存在完整有效R2时替换旧R0，R2无论supported/partial/unsupported都同样适用，
包括内容指纹未变化的情况；缺失、非法或失败R2不替换。局部R2不冒充全范围判定；没有

### 五项调用与失败边界

1. 全文件逻辑模型调用仍为`L=S+A0+F0+[A1]+[F1]+B+W+Rb+C+R2`；方括号仅既有
   条件触发，单逻辑请求物理发送最多4次。S/B/W/R按实际完整工作集数量增长，本次
   不增加每章/每规则模型调用或两两组合。拆目标可使W/R分包数变化，不能承诺调用数
   固定。检索新增唯一查询最多为无适用意图、具精确原文且明确需要knowledge的显式
   内容位置及响应行数；按原文、固定知识范围/版本及原件模式去重，不按所有规则×目标展开。
   物理知识HTTP仍按单操作`≤4(Q+D+K)`，成功空结果不再换问法。
2. A最坏输入是全候选树、去重后的候选规则语义、全部必要原文与反馈；增量随候选-规则
   显式关联增长。输出是完整采用树及实际scope选择，随树/选择边数增长；不能让模型
   重抄原文。F输入仍是完整采用树及去重原文，W/R按实际依赖计量。输出预留不是API
   硬限，无法保证任意文件的completion固定封顶；记录真实usage并沿现有完整JSON/结束
   合同接收，不静默截内容。最终请求超估算仍保留已授权发送路径，不上调窗口以过关。
3. 未分配范围由宿主保留待整理；跨候选/非法scope由现有合同纠正，耗尽保留安全大纲；
   复合规则、参见歧义、缺查询及复核不可用均明确待核/待补。部分流不采纳、不记零费用。
   草稿/Word/ZIP继续生成，存储/取消/失租等真实技术失败不伪报成功。外部断流不改
   超时、代理、TLS或模型来猜修，不与容量改善混为同一已解决根因。
4. S合同不变，可按完整请求摘要复验旧S回包；新A规则映射/Schema会使A0/A1变化，
   新表示会使F变化，受影响查询/W/R按实际依赖重算。唯一成功请求可回放，不清缓存、

   修订仍只有C/R2，范围修订没有额外循环。
5. 模型只选实际范围/规则并做语义组织与核对。正式身份、编号、来源回绑、并集保全、
   查询去重及版本采用由宿主完成；不要求回抄全部候选、原文、覆盖清单或CAS元数据。
