# 修复与改进路线

2026-11-19 制定。依据：设计评审（BUG-251 至 260）、按「双轴正交模式」框架做的对照，以及逐条代码核实。做完一个工作流就把结论并入权威页，并从本页删掉该工作流；全部做完删除本页。

## 目标

让第一份真实文件通过[最低验收线](../docs/tender/acceptance.md#最低验收线)（0/4 → 1/4），再到 4/4。过程中做到三件事：

- 每次运行都能说清卡在哪一层；
- 每次运行的成本有上限；
- 改一处只影响一处。

## W2 一条要求链

核心决定（2026-11-19）：

1. 分析事项台账是编制唯一的要求来源，编制只决定「放在哪、怎么写」，不再逐原子重新分类全部原文（BUG-254）；以试点实测为准。
2. 保真范围仅限原式表格、固定文字、签章位置（宿主从冻结网格原样复制），其余正文用解析文本加引用；解析瑕疵记为解析器缺陷。
3. 整稿重新生成产出新稿、不合并旧稿，当前交付「整稿加人工编辑」，AI 定点候选入稿推迟。
4. 第一份真实文件过最低验收线前不新增协议或阶段；旧链（A、M、B、C、P、F、原文选择）只修对照必需缺陷，验收切换后连同 `validate()` 已不可达的 `locate`/`associate` 分支一起删除。

目标链路：

```text
分析  register → freeze → extract → verify → [confirm] → 事项台账（带证据引用）
编制  ① 结构：格式章节 + 提交类事项 → 分册、章节、原式表
      ② 归属：事项短 ID + 章节树短 ID → item_id 对应 target_id
      ③ 原式填充：宿主复制原表，模型只填有依据的格子
      ④ 依据 / 写作 / 复核 / 改稿（沿用）
      ⑤ 导出 DOCX → ONLYOFFICE
```

五问答辩：

1. 调用：分析 `P`；编制 = 结构 `k`（格式章节包数）+ 归属 `⌈事项数/批⌉` + 依据批次 + 写作 `T` + 复核批次 + 至多 1 次改稿和 1 轮再核，线性增长，无读全文请求。
2. 最坏输入：各阶段按预算分包；结构只读格式章节，装不下按章拆。
3. 新问题与出口：分析漏报走待核/修订；归属不到位置进缺口清单由用户在 Word 安排；解析错误进解析器缺陷。
4. 修订：来源变化重跑受影响包、归属与任务；只改事项重跑所在归属批次与关联任务。
5. 誊写：归属与填格只回短 ID 与填值。

试点必须验证闭环的三类真实场景：

1. **非事项说明性背景接入**：把项目背景、现状、业务规模等非事项来源范围按引用绑定到技术方案等章节。
2. **空偏离表 / 逐条响应表展开**：遵循[条款号规则](../docs/tender/workflow.md#f-原式的条款号)，核验表头、项目信息、签章与固定注释的相对位置。
3. **未确认分析下的跨文档补遗隔离**：来源集含未决补遗/澄清时同时保留标示，避免静默混用旧条款。

| 3.5 | 按故障域拆分重试额度（BUG-260）：传输类（429、5xx、断连）和合同纠正类分开计数且传输计数持久化；同端点 429 单进程内并发槽位共享冷却窗口 | 3 次 429 后仍保留完整纠正次数；Worker 重启后传输计数不归零；冷却期内同进程其它槽位不发请求；实施前先改业务工作流 |

3.2 五问：不增加调用只截断；单次请求不变；新问题是产物不完整，出口是缺口清单加人工补或提上限重跑；修订只重跑被截断任务；不涉及誊写。

3.5 五问（建议值：传输 4 次、纠正 2 次，待基线确认）：单逻辑请求物理调用上界变为「传输+纠正」并受 3.2 运行上限约束；单次请求不变；新问题是冷却期变慢，出口是心跳、取消与运行上限；修订不变；不涉及誊写。

## 不做的事

- 不在第一份文件过线前新增协议或阶段（W2 替换和 W3 上限除外）。凡改变请求格式、回包字段、分包规则或事项语义的修复都算协议变化，须先答五问并说明为什么不能等到过线以后。
- 不用有损摘要压缩原文，不引入主 Agent 自由调度或模型自行调用工具的循环。
- 不为兼容旧运行而保留两条链。
