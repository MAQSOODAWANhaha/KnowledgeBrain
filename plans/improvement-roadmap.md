# 修复与改进路线

2026-11-19 制定。依据：设计评审（BUG-251 至 260）、按「双轴正交模式」框架做的对照，以及对一份外部分析的逐条代码核实。做完一个工作流就把结论并入权威页，并从本页删掉该工作流；全部做完删除本页。

## 目标

让第一份真实文件通过[最低验收线](../docs/design/python-tender-phase1/acceptance.md#最低验收线)（0/4 → 1/4），再到 4/4。过程中做到三件事：

- 每次运行都能说清卡在哪一层；
- 每次运行的成本有上限；
- 改一处只影响一处。

## 顺序与依赖

```text
W0 收口工作区 ──► W1 可观测性与评测基线 ──► W2 一条要求链（实测 → 替换）──► W4 路由与经验
                                         └──► W3 治理（与 W2 第 3 步并行）
W5 工程卫生：全程并行，不阻塞主线
```

W1 必须在 W2 实测之前完成：没有统一的度量，新旧链路的对比就没有可比的依据。其中 1.6 是 W2 的硬前提：W2 让分析台账成为编制唯一的要求来源，而 222 实跑显示一个抽取包漏处置了 45% 的范围，包括评分和报价条款。

| 里程碑 | 判定 |
| --- | --- |
| M1 工作区收口 | W0 完成，全量测试（含 PostgreSQL 集成）通过，按主题提交 |
| M2 有基线 | W1 完成，一份真实文件有人工标注，能自动算出最低验收线四项指标 |
| M3 1/4 | W2 新链在基线文件上通过最低验收线 |
| M4 4/4 且有上限 | 四份真实文件通过；W3 的运行上限和待核队列上线 |

## W1 可观测性与评测基线

不增加模型调用（五问第 1 问的增量为 0），只增加宿主统计和人工标注。

| 步骤 | 做什么 | 怎么验证 |
| --- | --- | --- |
| 1.1 | 执行阶段报表：已实现为只读投影 `cli authoring-report <execution_id>`（不写产物、不改执行身份，旧执行也能看），按阶段列逻辑和物理调用、Token、状态，以及响应位置、知识应答、规则引用、issues 和缺口按 code 计数；字段见字段字典。分析侧 `budget_observation` 不再等待已退役阶段。剩余：Web 执行详情展示 | 完成（CLI）；单测覆盖报表和 CLI 回读大纲 |
| 1.2 | 真实标注基线：选 1 份真实文件，人工整理「适用要求清单」（以分析事项为底，补漏）和「指定格式表清单」（列数、表头、合并）。只存仓库外证据目录 | 标注由人确认；仓库只放合成的样例结构 |
| 1.3 | 评测脚本：读一次执行的大纲、Word 和报表，按最低验收线四项打分，输出漏项和错表的具体位置 | 对旧运行产物离线跑一次，得到当前基线分（预期不过线） |
| 1.4 | 机器侧失败分类：把拒收回执、待核 code 按运行聚合成一张表，按「阶段 × code × 失败消耗的 Token」回答「哪类失败最多」；bug-fix.md 只记根因 | 对同一运行，聚合数与回执行数一致 |
| 1.6 | **分析抽取完整性（BUG-261，W2 的前提）**：① 按输出工作量分包，用 222 实测（每条处置和每个事项的平均输出 Token）校准抽取输出预留，单包预计输出不超过预留；② non_item 允许按「同一理由一组范围」紧凑声明；③ 抽取 Prompt 删掉「漏写留给 review」，要求每个未被引用的范围都给处置；④ 确认页按类型和页面分组，支持批量处理格式碎片 | 同一份 222 重跑：未处置范围占比低于 2%；人工抽查第 35 到 76 页的评分、报价条款都已成为事项或有处置；人工问题数和 Token 与本次对比，写入交接 |
| 1.5 | Web 展示：报表接入执行详情；进度里的 locate、associate、joint 改为「仅历史运行」显示；`total_units` 由宿主按计划数给出，给不出时明确显示「未知」 | 新旧运行的进度页都能正确显示；不增加模型调用 |

需要你决定：用哪份文件（建议 222，规模小、已有较多回执）；谁来做人工标注。

## W2 一条要求链

细化步骤、五问和风险见[一条要求链](single-requirement-chain.md)。这里只补三条增强要求，在第 3 步写新链时一起落实：

1. **上下文分诊：** 结构阶段只读格式章节，归属阶段只读事项摘要和短 ID，原文由宿主按引用装载；不再有读全文的请求。
2. **技能包：** 新链每个任务是一个有版本的单元（Prompt、输出 schema、宿主校验器、测试放在一起）。请求组装走一条固定顺序的链：来源装载 → 短引用编码 → Prompt 片段 → schema → 纠正反馈 → 预算准入，每一步都是纯函数，并登记自己增加的输入和输出上限，五问第 2 问从这条链直接算出来。
3. **删旧路径：** 新链验收后删除 A、M、B、C、P、F、原文选择的旧代码和 Prompt，以及 `validate()` 里已走不到的 locate、associate 分支，不两条链并存。
4. **表示收敛：** 新链上线时列出要删除的平行表示（原生 B/C 的原子账本、目录编译中间结构等）。每种保留下来的表示都要写明「从冻结源怎么派生、身份是什么」，派生字段不进入源身份摘要（参照 BUG-255）。

## W3 治理

| 步骤 | 做什么 | 怎么验证 |
| --- | --- | --- |
| 3.1 | 执行身份只包含本执行实际调用的任务的 Prompt 和契约哈希（BUG-259） | 只改 verify Prompt 时，编制执行身份不变；改 write Prompt 时，分析执行身份不变 |
| 3.2 | 运行级上限：每次执行设总逻辑调用数和总 Token 上限 | 上限触发后，剩余任务全部以具名待核出现在缺口清单；已完成内容照常导出 |
| 3.3 | 编制待核人工队列：Web 按响应位置列出待核，可标记已处理、补资料或接受空缺；统计每份文件的待核数和处理时长 | 基线文件的待核全部能在队列里看到并处理；指标进入 1.1 的报表 |
| 3.4 | （可选）对抗评审：允许 verify 和 review 按任务配置独立模型和 reasoning_effort | 先用 W1 基线比较同模型和异模型的漏检率，有明显收益才上线 |
| 3.5 | 按故障域拆分重试额度（BUG-260）：传输类（429、5xx、断连）和合同纠正类分开计数；同一端点收到 429 后，所有并发槽位在冷却窗口内都不发新请求 | 3 次 429 之后仍保留完整的纠正次数；一个槽位收到 429 时其它槽位不发请求；实施前先改业务工作流的五问 |

3.2 的五问：

1. 不增加调用，只截断；
2. 单次请求不变；
3. 新问题是产物不完整，出口是缺口清单加人工补或提高上限重跑；
4. 修订只重跑被截断的任务；
5. 不涉及誊写。

上限的具体数值建议取 W1 基线实测的 2 倍，已确认。

3.5 的五问（建议值：传输 4 次、纠正 2 次，待实施时按基线数据确认）：

1. 单个逻辑请求的物理调用上界从 4 变成「传输次数 + 纠正次数」，全文件仍受 3.2 运行级上限约束；
2. 单次请求不变，纠正请求沿用 BUG-221 的有界反馈；
3. 新问题是冷却期内整体变慢，出口是心跳、取消和运行级上限；
4. 修订不变；
5. 不涉及誊写。

## W4 路由与经验

| 步骤 | 做什么 | 怎么验证 |
| --- | --- | --- |
| 4.1 | 复杂度路由：格式章节明确、表格齐全的文件走宿主的 `bid_format_plan`，不调模型；判定条件写进业务工作流 | 基线文件上两条路径的验收分相同，轻路径调用数更少 |
| 4.2 | 经验回放：人工裁决（待核结论、修订）沉淀成回归样例，进入语义评测语料；改任何 Prompt 前后都跑一次 | 新增样例覆盖基线文件的每类人工裁决 |
| 4.3 | 多模态：按 W1 报表中未读图片影响的要求数，决定是否让 VLM 读图进入编制 | 有数据再决定，不预先实施 |
| 4.4 | 跨批依赖组一致性复核：只核报价、配置、工期、人员、核心参数这类共享约束组，不做全章两两比较；在 W2 新链之后做 | 基线文件上人为制造一处跨章矛盾能被报出；调用增量按依赖组数线性，写进业务工作流 |
| 4.5 | （待数据）由显式引用（如「见第三章 3.2 节」）触发的有界一跳补读 | 先看 W1 报表里「因引用未决留下的待核数」；与「过线前不新增协议」冲突，过线后再定 |
| 4.6 | 知识检索有界并发（`authoring_knowledge.py` 目前逐条串行） | HTTP 次数不变，耗时下降；恢复额度和回执语义不变 |

4.1 的五问：调用只减不增；单次请求不变；新问题是误判为简单文件，出口是验收分下降时回退到模型路径；修订不变；不涉及誊写。

## 不做的事

- 不在第一份文件过线前新增协议或阶段（W2 的替换和 W3 的上限除外，它们是减少调用和设上限）。

- 不为兼容旧运行而保留两条链。
