# 目录计划

source_line_format=numbered_line_pairs_v1 时，每页 lines 中每项为 [零基行号, 完整原文]，不是改写或省略。所有行和空行均保留，来源坐标继续按给定 document_id/page/行号选择；不得用数组位置替代明示行号。

只根据本次给出的已登记文件，标出投标文件目录所需的位置和采用决定。不要写章节标题、模板正文、企业名称或另一套正式名称。名称、父子、顺序和原文搬运由宿主完成。

每份文件有 document_id 和 role。role 只可能是 main、attachment、clarification、amendment。page 和 line 从 0 开始，line 只在该文件的该页内计数。每个位置都必须带 document_id。一份组成清单的条目必须来自同一个文件。

补遗（amendment）或答疑（clarification）中的组成清单，priority_basis 必须包含该文件里写明其效力的连续原文窗口。没有引用的补遗或答疑不要拿来改写组成，也不要按文件先后猜测哪一份优先。

组成清单决定应提交哪些内容，不是这些内容的模板正文。原文明示分为多个独立文件、组成分组或上传模块时，每组使用独立 scope，title 指向该组名称的原文行；组内采用项放入对应 scope。不要把分组条款再建为同名正文根章。原文没有分组才使用 title:null，不为所有项目固定造分组。

每个 node 必须返回 body_windows 数组，窗口只使用 document_id、page、start_line、end_line，起止行均包含。明确没有需要搬运的原式或直接响应正文时返回 []。每个窗口在同一文件的一页内，多页正文逐页列窗口。宿主只搬这些窗口，不会自动从标题复制到下一个标题。

每个 node 必须明确 response_kind：form 是保留原式、原表及其原有填写空位；narrative 是需要投标人逐段应答或编写方案的要求，宿主在原要求后保留人工应答空白；attachment 是需要另附真实证明、授权或承诺函的位置。不要把技术要求全部标成 form，也不要把原式固定声明改为自行编写。纯容器可以 body_windows:[]，但实际待交材料必须有可填或待附出口。没有企业资料不等于删除材料，也不等于已承诺响应。

原件给定的投标封面也是必查原式，不属于可省的导航。完整选择其项目名、投标人盖章、代表签字、日期等实际源字段；不得以软件默认的“投标文件”标题代替。封面采用项用 presentation:cover、depth:self，response_kind:form，body_windows保留原式和空位；共用整稿封面可独立放在title:null的scope，宿主将其置于目录前。只有原文要求独立分册封面时才分别承载，不凭空增加公司名、项目值或签章。普通无标题正文才使用content，真实章节使用section。

同一组原式要求多个主体分别提供时，在该 node 的 subjects 中逐一选角色。每项给 source 原文窗口和 role 原文中的短角色片段，不写公司名；例如原文明确两个主体时选择两个角色，宿主在同一章节保留各自完整原式和填写位置。没有分别提供要求时 subjects:[]，不能自行增造实例；主体是否为同一家公司未知时仍保留分别提供的边界，不能无依据合并。subjects 只限定本章原式/正文实例，不把另行归入的某主体专属要求扩大到其他主体。

heading 是章节名称的来源锚点；body_windows 是实际原式或需逐项应答的技术正文，二者可以位于不同位置。不能从“技术文件包括……”等组成说明开始，跨过招标须知或评标办法一直搬到格式章。只有投标人需要提交/填写/逐项应答的原式和直接响应内容进入模板；评标人员使用的资格审查、评分工作表不作为投标原式，其义务和评分依据由后续章节要求提取。

父节点的窗口只列父章自身正文；子节点的正文由子节点自己的窗口承载。相同来源的原式在同一提交实例中只由一个节点承载，其他名称或参见关系用 format_bindings，不因为来源书内的“部分/专用部分”等容器标题另造一份相同提交物。确有不同主体或独立提交实例的重复须保留真实组成依据，不能按相同文字机械删除。

原式可以位于另一份文件。content_start 仅用于标题之前已有原式内容的情况，必须与标题在同一文件且不晚于标题；它不代替 body_windows。每个来源节点都要有去向：采用、排除并给出原文依据，或标为 source_only。目录/组成说明/仅供理解的来源节点使用 body_windows:[] 并明确去向，不能默认为正文。组成条目要么被采用，要么用 excluded_by 指向不适用依据。

投标文件要响应的内容不只有格式章。招标文件用标题单独列出、并要求投标人分别响应的部分，按真实组成和来源层次选节点，heading 指向该标题行。要求技术文件采用某卷/规范的结构、格式和顺序时，保留该来源的通用部分、专用部分等真实容器与先后顺序，不能借用另一处格式章标题作技术父章，也不能把通用正文全改挂到专用部分后声称结构相同。参数表里的单个字段和财务表每行不要各作一章。无来源依据不另造顶层章节。

技术规范中要求填写的供货范围、技术数据、偏差和保证值等附表，即使不在集中格式章，也要按真实组成和适用条件纳入。只按本次原文明示的不适用依据排除；缺少企业资料、还未选型或无法判断制造商/代理商身份，不是不适用依据，应保留条件和待填原式。

排除依据只能排除它真正限定的义务与实例。投标时提交的承诺、其下附的规定格式和中标后实际开立/缴纳的义务须分别判断；后续实际开立不要求，不能自动删除组成清单明列的投标承诺及原式。来源之间适用性未能明确时保留原式及相关条件，标为人工核定，不能用整项排除消掉冲突。专用部分明确某材料本次不适用时，其通用条款也不能借另一个可选材料重新成为本次义务。

采用项的 condition 专门引用尚待企业身份、选项或招标澄清核定的适用条件原文，宿主据此生成具名的“适用性待人工核定”记录和处理栏。凡保留了原式但本次是否提交/履行尚未明确，必须选 condition 指向导致待定的原文窗口；其他组成或效力依据仍可放 clause。只在 clause 并列两处原文不会建立待核决定。条件明确无需待核时才 condition:null；不要让缺少企业身份或相互未决的源要求变成默认已确认。

附表、别名和组成清单里的另一名称是否共用同一份响应数据，写在 format_bindings：给出说明这层对应关系的原文窗口、实际承载数据的节点编号，以及引用它的节点编号。数据共用不等于删除原件给出的原式：已有表框、固定参见文字或填写空位的引用型原式，仍须通过该节点的 body_windows 完整保留；不再抄写另一表的实际数据。仅有名字、没有原式且原文明示不另交时，才可以作为无正文引用。clause 仅选正文之外的适用说明，不用 clause 代替原式表格。不要根据「附表」或编号改标题，也不要另造章节名。

只返回 JSON。字段以宿主附带的 Schema 为准，不要增加 Schema 以外的字段。
