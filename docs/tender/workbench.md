# 投标编制工作台、Word 导出与 ONLYOFFICE

外壳颜色、页面框架、导航联动和组件选用只以 [DESIGN.md](../../DESIGN.md) 为准；业务流程与字段合同分别见 [业务工作流](workflow.md) 和 [字段字典](field-dictionary.md)。本页统一约束前端工作台交互、来源格式进 Word 与 ONLYOFFICE 编辑、保存和同版 PDF 出件。

## 核心决定与页面行为

- 正式标书直接在 ONLYOFFICE 中展示和编辑 DOCX，DOCX 是正文唯一正式编辑入口。网页承载文件导航、招标要求、采用依据、待补事项和执行状态。
- 左右侧栏均可收起；窄屏右栏改为抽屉（跟随编制区不写死视口顶部像素），正文编辑区保留至少 420px，高度不足时工作区纵向滚动。
- 打开稿件默认阅读，进入编辑操作同一份 DOCX；工具栏明确区分当前查看稿件、已保存版本、编辑中修改及后台生成任务；页面操作使用“生成新稿 / 保存修改 / 下载已保存稿”，不要求额外“同步到 Word”。
- 执行进度来自真实回执，不伪造百分比；任务失败、文件已形成、资料待补和内容待核对分别表达，不合为一个“完成”状态。各阶段显示已接受单元和宿主登记的计划数，没有计划时显示「计划数未知」，整体总量显示「未知」；已退役的定位原文、关联要求、联合核验只在历史运行中出现，标注「仅历史运行」。
- 招标解读页头状态按执行状态区分 分析中 / 分析失败 / 已取消 / 需要处理 / 待人工确认 / 已确认，分析未完成时不提示可确认。事项的原件位置显示物理页（「第 N 页」），没有页码时显示标题路径，不显示内部范围编号。分析失败时恢复区列出失败回执原因（区分工作单元用尽、基础设施故障与执行配置变化 `execution_config_changed`）和模型调用错误类型与次数，恢复理由必填。
- 「执行详情」抽屉展示当前编制执行的只读报表（各阶段逻辑请求、实际发送和 Token，失败分类按 Token 排序，字段见[字段字典](field-dictionary.md)的 `authoring-report`）；打开抽屉才读取，读取不发模型请求。

| 情形 | 中间区域 | 目录与右侧信息 |
| --- | --- | --- |
| 首次生成，尚无 DOCX | 显示实际执行阶段、已形成大纲与等待/失败原因 | 展示可读结构、要求与问题；未知保持未知 |
| 已有 DOCX | 直接打开该版本真实稿件 | 展示对应版本目录与已绑定要求、依据、缺口 |
| 已有稿件，后台生成另一稿 | 保持当前稿件可读可编辑 | 提示后台任务进度，不重载编辑器 |
| 新稿已形成 | 提示“查看新稿 / 继续当前稿” | 用户显式选择且当前修改妥善处理后切换 |
| Word 服务暂不可用 | 显示重试与最后已保存稿下载入口 | 保留已读取项目与业务信息 |

## 目录、大纲编排与版本边界

- **项目来源设置**：在「项目资料」中核对已上传文件角色。文件已保存但登记未完成时，按文件重试登记。文件上传、登记状态变化或并发保存使来源令牌变化时，工作台保留未保存编辑并要求重新加载。操作见[运行手册](runbook.md#提交与确认当前-v2)。

- **目录与锚点**：左侧展示分册、章节、表单及附件位置，点击定位 Word 并切换右栏；稳定身份写入 Word 锚点并绑定版本，锚点缺失/删除提示“位置需要重新关联”，不跳相似标题。目录切换与展开侧栏保留编辑器与未保存修改；Word 光标联动右栏需单独验证，不作为默认能力。
- **大纲编排**：编制页提供“大纲编排 / 正文编辑”两视图（切换保留 Office 实例与各自修改状态）。独立“生成大纲”只产出候选，不替换已保存大纲或未保存修改。大纲树支持新增同级/子级、改名、删除、上移下移和缩进提升，移动只用章节位置工具条，不做拖放；删除章保留原招标规则及未安排问题。
- **评标待核裁决**：大纲问题里由模型建议按评标程序处理的事项，在大纲页显示待核数量。「核定评标待核事项」打开抽屉，按事项原文逐条选择去向：继续待核、纯评审流程、原文索引、整份约束，或归入本次大纲中的一个响应位置。核定与章节调整一起计入未保存修改，「保存大纲草稿」时只提交改过的事项（见 [字段字典 · 新链事项归属](field-dictionary.md#新链事项归属)）；保存成功后离开待核列表，重选已核定去向从核定前历史大纲另存。
- **项目背景选择**：在大纲编排的章节「关联响应」中，可为可写知识型正文目标（`kind="narrative"`、非 `manual_fill`、`support_origins=["knowledge"]`、无原式表且非 `source_body_contract`）打开「选择项目背景」抽屉，筛选并勾选当前冻结主件的原件范围，随「保存大纲草稿」通过 `source_additions[].project_context_excerpts` 保存。来源角色待核或存在补遗、澄清时展示原因并禁用选择。
- **分析修订与历史大纲**：已保存大纲显示使用的分析修订；有较新可用分析修订时返回 `newer_analysis_identity` 并提示可生成新版候选，仍可用固定旧修订生成正文。“按大纲生成正文”只使用平台已确认保存的具体修订与摘要；历史大纲可预览对照并另存修订，未安排响应可迁至选定章；目录读取失败明确显示未知，不以 0 项掩盖。
- **右侧要求、依据、待补与离开保护**：要求显示原文/条件/定位；依据区分招标原文、企业资料与证明原件；待补项标明缺失与动作，报价保留原表空位；复核意见绑定稿件版本，人工补写后原意见留待核对。可从「更多操作 → 编制待核队列」或右侧「待补」栏打开「编制待核队列」抽屉，按响应位置（章节与目标）分组查看全部待核项，支持跳转 Word 书签、记录备注并标记「已处理 / 补资料 / 接受空缺 / 恢复待核」（未保存备注跨轮询保留），待核计数与处理时长统计汇总进「执行详情」（`authoring-report`）。项目资料页可选择知识资产固定版本并在提交正文时冻结（后台不存用户令牌）；招标解读页支持按问题类型与判定状态筛选、分页浏览并批量或逐项人工判定，同时支持对照冻结原文分页纠正事项业务字段并重审。人工输入、未知请求、大纲、待核备注与 Word 未保存修改均纳入离开保护。

## 保存、下载、AI 边界与接入实现

1. 修改后显示“有未保存修改”；点击保存显示“保存中”，服务端确认会话、父版本、结果版本与文件身份一致后才显示“已保存”；网络中断/回执未知显示“保存结果待确认”并重试同一次请求；明确失败保留现场与修改标记。
2. 下载使用明确已保存版本（有未保存修改时明确提示不包含），不依赖资料齐备或问题关闭。
3. 当前交付「整稿加人工编辑」：整稿重新生成另存新稿，不合并旧稿，不覆盖用户已保存版本；编辑后 AI 候选入稿已推迟（见 [PRODUCT.md](../../PRODUCT.md)）；不把编译中间结构当成第二正文主源。
4. 接入实现：前端 [DocxEditor.tsx](../../web/src/bid/authoring/DocxEditor.tsx) 与 [docxSession.ts](../../web/src/bid/authoring/docxSession.ts) 对接 Rust `/api/v3/tender-projects` 权限、回调与版本保护（`crates/api/src/tender_editor.rs`、`tender_render.rs`，表 `tender_editor_sessions`、`tender_draft_*`，字段级协议见 [字段字典 · Word 编辑器与 PDF 出件协议（v3）](field-dictionary.md#word-编辑器与-pdf-出件协议v3)）；Python [document_execution.py](../../services/docreader/tender/document_execution.py) 与 [authoring_export.py](../../services/docreader/tender/authoring_export.py) 经 `TenderBridge` 提供编制产物。页面查看、切换、保存和下载新增模型调用为 0，轮询刷新不得重复创建付费任务。

## 来源格式进 Word

PDF、DOCX、Excel 冻结为同一批来源对象，格式定义只在来源存一份；Word 还原来源已记录格式，不按原 PDF 逐页排版。模型只接收表格明文 `grid.rows`、非 1×1 `merged_cells`、阅读文本与身份并只回引用和应答；列宽、字体、页边距、页坐标及 `paragraph_breaks` 只留来源，由 `services/docreader/tender/authoring_export.py` 回查：

| 来源里的格式 | Word |
| --- | --- |
| 独立文本封面 | 封面目标通过 `source_refs` 绑定本次冻结 PDF 的标题单元。竖排标题逐字成行时，以同页已核对的首字单元定位。原文字行与该页逐行吻合时，按实测行位、字号和签署横线生成可编辑段落与填写位。无法核对几何时保留原文空行与字段，提示核对版式。 |
| 格子 | PDF 有边框的表按同一高度上连接两条实际竖边的横线确定行界和行高。局部行界保留相邻单元格的纵向合并，同格单行固定文字能与 PDF 原字一一对齐时，将文字间及两端可核对的空白填写线还原成可编辑的带下划线制表位。选中部分行时带上表头，空应答留空。 |
| 落在 `paragraph_breaks` 上的切点 | 新段落 |
| 没有对应切点的换行 | 并回原句，字中间断开的也并 |
| 上一行以 `。！？；：` 结尾，或下一行以 `13.`、`（1）`、`一、` 开头 | 新段落 |
| 冻结解析标记为重复页边文字的行 | 仅省略当前物理页首/页尾单元；同文字出现在表前后或其他正文位置保留 |
| 图片 | 嵌入原件 |

同一条要求既在表里又在正文里时两处保留；`text_boundaries` 不能单独决定合并，切点回来源 `paragraph_breaks` 核对。

## PDF 与报告

V3 出件页每个已保存版本可独立下载 DOCX 或 PDF。PDF 使用 `POST /api/v3/tender-projects/{project}/docx/versions/{version}/pdf`，请求体仅含 `docx_sha256`；权限沿用 DOCX 下载，请求摘要与实际 DOCX 长度/摘要不一致返回冲突，并发保存新稿时仍读取请求指定版本。

转换沿用 ONLYOFFICE 并发配额、文件上限、超时与下载地址校验，取源签名绑定项目、所有者、版本、DOCX 摘要与本次转换标识。成功返回 `application/pdf`，响应头 `X-KB-Render-Source-Version`、`X-KB-Render-Source-Sha256`、`X-KB-Render-Pdf-Sha256` 标明源版本与两份摘要。报告只包含实际执行的检查与已知问题。

## ONLYOFFICE 部署与验证

浏览器经 `KB_ONLYOFFICE_SERVER_ORIGIN` 加载 DocsAPI；API 经 `KB_ONLYOFFICE_COMMAND_ORIGIN` 调 CommandService；文件和回调经 `KB_ONLYOFFICE_API_ORIGIN` 回传 API；密钥不放前端，不默认依赖 Developer 版专属 Automation API。健康接口和示例页不等于验收，必须实测：

1. 真实 DOCX 打开、编辑、forcesave、回调落库、关闭重开和下载。
2. 图片、表格、标题、页眉页脚和样式在普通编辑保存后保留。
3. 同一 DOCX 转 PDF，源摘要和版本绑定正确；后续编辑不会让旧 PDF 冒充当前版。
4. 重复、乱序和失败回调、过期会话、并发保存都不覆盖新稿。
