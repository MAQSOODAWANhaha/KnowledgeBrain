## 1. 第一阶段做什么

只解析招标文件，产出一份投标文件模板，不填内容。验收只看三项（2026-11-10 用户确认）：

1. **目录**：名称、父子、顺序、条件正确。
2. **模板落章**：招标文件给的格式原文逐字落在对应章节，固定文字和待填位保留。
3. **章节要求**：每个应答章节有带来源的章节要求。

边界：

- 招标文件里没有的可以省略，不编造；原文要求但没给原式的提交物，只保留原句和条件。
- 跨章共同要求只要求原文保存完整，不要求精确送到每个接收章。
- 人工编辑和确认放在第一阶段全部结束之后，目录和后续环节之间不暂停。
- 目录质量是最高优先级，不为提速降低。

## 2. 现在的流程

入口 `outline::generate_first_stage`（`outline/generation.rs`），由任务 `Input::Outline` 分支调用。

| 步骤 | 谁做 | 做法 | 代码 |
| --- | --- | --- | --- |
| 准备原件 | 程序 | PDF/Word 转成带页码、行号、词坐标的阅读单元；页眉页码按正文边界剔除 | `runtime/`、`direct.rs::Source` |
| 扫描页 | 程序 | 文字少于 20 个的页渲染 300dpi 后 OCR（中英），结果进待确认提醒人工核对 | 预处理 |
| 目录计划 | Codex agent | 并行出两份独立计划。模型只标出“标题在原文哪里、采用哪份组成清单、哪些原式要采用” | `directory_plan.rs`、`outline-directory-plan-v1.txt` |
| 目录复核 | Codex agent | 第二步接收首份计划，复核来源并采用复核结果；两份计划的差异写入待确认 | 同上 |
| 目录编译 | 程序 | 按计划编译名称、父子、顺序、编号；模板按来源窗口逐字搬运 | `directory_plan.rs`、`generation.rs` |
| 章内材料来源 | 直连模型 | 一次全文调用，给出各章要承载的格式外原文范围；已被承载的行不重复复制 | `direct.rs`、`outline-chapter-materials-v1.txt` |
| 参数展开 | 直连模型 | 原文不少于 25 行的叶子章节按小标题和每条参数拆成子章；模型给每条的起止行 | `outline-parameter-expansion-v1.txt` |
| 章节要求 | 直连模型 | 原文按约 600 行分块（不切开一页），并发 2；每条给起止行和归属 | `outline-chapter-requirements-v1.txt` |
| 分类、采购分析 | 直连模型 | 与上一步同组并发，出处用行号 | `outline-classification-direct-v1.txt` |
| 表格还原 | 程序 | 按原件框线和词坐标还原单元格，含合并格、跨页续表；保存为 `source_tables` | `outline/tables.rs` |
| 结果 | 程序 | 校验后保存；疑点全部进 `issues` | `mod.rs` |

几个要点：

- **直连环节的统一协议**：全文带行号送入，模型只回行号，程序按行号逐字搬运。
- **章节要求的归属规则**：只归一章 → 该章要求；多章共同 → 限定这些章的共同要求；全文件 → 全文件要求；无法确定 → 待归属。已作为模板或材料搬入的行不再重复成要求。最后仍没有要求的叶子章节写入待确认，不编造。
- **缓存**：每个直连请求的回答按“模型＋提示词＋输入”的摘要保存，中断重跑时相同请求直接复用。副作用：同一文件重新解析时直连部分会复用上次回答，目录步骤仍重跑。
- **兜底**：两份目录计划都失败时回退到旧的首稿路径（`handoff::call`），按页引用工作，保证仍有结果。
- **失败处理**：直连单节失败写入待确认；429/5xx 退避重试；只有原件变更、配置错误、用户停止才中止整轮。

## 3. 演进过程

### 3.1 自建多步工具流（2026-09）

分包检查、逐包修复、交叉复核。修复轮不收敛，后来只能加墙钟上限、每包只修一轮、停滞的包跳过（提交 `S1 Check convergence`、`Cap Check repair at one round per packet`）。

教训：用“检查—修复”循环追求全对，循环本身成了不稳定来源。

### 3.2 整体迁到 Codex，一个会话交一份完整大纲（2026-10-18 起）

Codex 读完原件，写一份完整的大纲工作稿 JSON，宿主做结构校验。

2026-11-06 对同一原件 7 次正式大纲做了对比，暴露的问题见第 4.1 节：结果随运行变化、解析层丢结构、要求靠模型重抄、耗时在模型逐步操作。

同期一直在改提示词补规则。到 2026-11-05，大纲会话拼接的五份提示词共 21,506 字符，职责交叉，并出现互相矛盾的指令：一份规定逐项参数材料 `uses_tianqing=true`，另一份规定其余一律为 false。

教训：一个会话既要读全、又要判断结构、又要抄原文、又要写长 JSON，每一项都会出错，而且错在哪一项分不出来。

### 3.3 来源片逐片提取 + 接收核对（2026-11-06 至 11-09）

把原文切成连续来源片，逐片让 Codex 提取要求；再加一步“接收核对”，把每条义务送到所有应该接收它的章节；还有结构纠正、要求撤回等机制。

结果（2026-11-09 实测）：

- 生产入口完整冷跑：Bid 2336.66 秒（约 39 分钟），111 3010.27 秒（约 50 分钟），两份业务验收都没过。
- 接收核对单步：Bid 956.31 秒，111 分 10 批共 1481.87 秒。
- 接收核对提示词一轮内从 1KB 涨到 8.7KB；一天内 `fix-bug.md` 新增 62 处记录。
- 冷跑多次以 `OUTLINE_SOURCE_UNRESOLVED`、读取截断无法恢复而失败。

2026-11-10 的诊断：问题不收敛的主因是把“每条义务精确送到所有接收章”当成自动全对的目标。这类归属没有原文可以对照，每次运行都会抽到新错例；又没有冻结的验收口径和停止门槛，逐个反例加规则，规则之间再产生新失败面。

教训：目标本身没有客观答案时，加再多规则也收敛不了。

### 3.4 目录计划 + 宿主编译（2026-11-09，`ce02d97`、`b5ed93e`）

- 模型不再写目录，只标出来源标题和优先组成清单的位置；宿主编译名称、父子、顺序，逐字搬运模板。
- 两次独立解析，差异转待确认项。
- 目录锁定后只归未覆盖的原文；单片失败重试后转待确认，第一阶段不因单步失败中断。
- 已完成步骤可复用；只有原件变更、配置错误、用户停止才中止。
- 删除旧路径：完整生成、来源审查、最终目录复核、结构比较及对应提示词和测试。

### 3.5 目标收窄 + 目录之后改直连（2026-11-10，`320bb7c`）

- 用户把验收口径收窄为第 1 节的三项；删除接收核对步骤。
- 先做可行性验证（第 4.2 节），结论是目录保留 Codex 计划＋复核，其余环节改直连。
- 新增 `outline/direct.rs`；删除来源片路径（`source_parts.rs`、`source_extraction.rs`、`structure_adoption.rs`）及其提示词、Schema 字段、运行时钩子和测试。
- 加入表格还原、扫描件 OCR、直连缓存。
- 冒烟：Bid 12.4 分钟、87 章、35 张 Word 表格；111 17.6 分钟、185 章、121 张表格；目录、模板、参数、章节要求均 0 差异。

### 3.6 收尾修正（2026-11-11）

- Worker 运行底座升到 Debian trixie，poppler 与开发机一致，表格线解析结果不再因环境不同而不同。
- 表格线解析兼容 `style` 写法；提取失败记入大纲问题而不是报错。
- 附件名称支持从引用清单跨行取得；参数表展开时合并与指标同名的类别。
- 阅读截断由拦截改为记问题；填充计划与附证的局部错误只记问题。
- 跨页参数续文、相邻条款串入的修复。

## 4. 关键实测数据

### 4.1 整份大纲由一个会话生成时的问题（2026-11-06，同一原件 7 次正式大纲）

- **结果随运行变化**：886 个确定性切分片段里，7 次都覆盖的只有 102 个，部分覆盖 205 个；两两 Jaccard 0.53 到 0.75；节点数 68 到 97。（7 次提示词版本不同，差异不全是模型随机性。）
- **要求靠模型重抄**：正式要求条目中能近乎逐字对回原文的只有 61% 到 79%。
- **解析层丢结构**：`pdftotext -layout` 把前附表的条款名与内容混排、跨行内容切开。
- **耗时在模型逐步操作**：一次 1785 秒的任务，模型调用间隔占 1744 秒，143 个响应串行；写工作稿 44 次共 826 秒，回读工作稿 41 次共 493 秒。上下文膨胀是次因。
- **根因判断**：系统没有确定性的条款单元，输出是模型一次选择性摘录，无法区分“判为无关”和“漏掉”，读完与否只能靠模型自述。

### 4.2 目录能不能直连（2026-11-10）

| 做法 | 结果 |
| --- | --- |
| 单次直连出整份目录（快速模型） | Bid 90 秒、111 163 秒，行号全部有效；但 Bid 目录差异 11、模板差异 13：漏封面原式、跳过“供货要求”层、附表挂错父章 |
| 单次直连出整份目录（推理型模型） | Bid 两次差异 11/18，111 两次 2/11；同文件两次规范化树差异 Bid 147、111 343 |
| 双读后再裁定 | 两次读取差异 119/290；两次共同的漏项不会出现在差异里；111 裁定只交回部分目录 |
| 保持计划协议、把 Codex 换成直连（检查不过带错误重试，至多 3 次） | Bid 运行 40 分钟没有一份计划通过宿主检查。反复被拦：引用行号差一行、名称来源未明确选定、条件不是原文片段 |
| 现有 Codex 计划＋复核 | 111 三次 6.4/6.4/10.3 分钟，目录 0、模板 0，三次树完全一致；Bid 三次 15.9/17.8/7.5 分钟，目录 0，模板差 1/3/3（都在附表段落） |

结论：

- 不稳定主要来自规则选择（名称取组成条款还是格式章、分组层级），这些正是由宿主编译的部分。
- 现有目录计划格式依赖 agent 循环里的多轮自查修正，模型无法一次交出合格稿。
- 目录步骤慢在代理循环：单步 35 到 43 次往返、150 万到 220 万输入 token，耗时随网关排队波动。

### 4.3 参数展开直连（2026-11-10，通过）

- 只给技术章节原文、单次直连。首轮两种模型在 111 都漏同样 5 条：多栏表格里子指标名称行夹在内容中间，按名称行切分会把首行分给上一条。
- 改为模型另给每条内容的首行，程序按首行到末行搬运后，两种模型、两份样本全部 0 差异。
- 快速模型 Bid 18 到 19 秒、111 53 到 66 秒，各 3 次均 0 差异、节点数一致。
- 推理型模型更慢（130 到 250 秒），且出现过重复节点，没有采用。

## 5. 让它稳定下来的改动

### 5.1 模型只定位，程序搬运

最有效的一条。模型不再输出目录标题或模板正文，只回答“在第几页第几行”，文字由程序从原件逐字取。

- 同时消掉三类问题：抄错字、编造原文、长输出被截断。
- 行号比字符偏移可靠：早期让模型给字符偏移，出现截字、越界、混入页眉；直连计划里“行号差一行”也是常见拦截原因，所以协议里起止行都要给。
- 起点要显式给：只给名称行让程序自己切，会切错多栏表格（第 4.3 节）。

### 5.2 目录由 agent 定位、程序编译

- 模型交的是“计划”：来源标题位置、采用的组成清单、采用哪些原式。
- 名称、父子、顺序、编号由程序按固定规则编译。稳定性来自编译规则，不来自模型。
- 目录需要 agent：要在组成条款、目录页、格式章之间来回翻看和自查，一次调用交不出合格稿。

### 5.3 命名规则由程序定，不让模型选

- 原式节点取原式标题。
- 原式标题只是组成名称加修饰（如“投标函的格式”）时，采用组成名称，不报差异。这条不靠词表，靠“是否包含组成名称”判断。
- 措辞确实不同时采用原式标题，并写入待确认。
- 之前让模型通过字段选名，同一文件两次运行取法不同；改成固定规则后删掉了“需要选择正式名称”的拦截和 8 个相关测试。

### 5.4 收窄目标

见 3.3、3.5。收窄后才能删掉接收核对、结构纠正、要求撤回这些步骤，时间和失败面一起降下来。

### 5.5 疑点转待确认，不拦截

- 校验和门禁多次让本可出结果的运行整轮失败。
- 现在进 `issues` 的有：两份计划不一致、名称措辞不同、表格提取失败、OCR 页、单片重试后仍失败、叶子章节没有要求、阅读截断。
- 硬拦截只留给会破坏原文可信度的情况：来源不能回读、编造原文。
- 新增校验前先问：它是帮助产出结果，还是阻断结果。

### 5.6 两份独立计划对照

并行出两份目录计划，差异直接成为待确认项，比让模型自查更能暴露不确定的地方。
局限：两次共同漏掉的内容不会出现在差异里（第 4.2 节双读实验已证实），所以它只能发现分歧，不能证明完整。

### 5.7 输入按范围切小

- 参数展开只给该技术章节的原文。
- 章节要求按约 600 行分块，不切开一页，并发 2。
- 每个请求输入范围明确，快速模型就够用，而且可以独立缓存、独立重试。

### 5.8 缓存和续跑

- 直连回答按请求摘要缓存；Codex 会话持久化，交付有错时在原会话里修，不重开。
- 同项目任务互斥认领，避免并行任务抢同一会话。
- 中断后只补未完成的部分。没有这一条时，直连部分中断要整段重做 2 到 4 分钟，Codex 部分更久。

### 5.9 表格由程序按几何还原

- 用 `pdftocairo -svg` 取框线、`pdftotext -bbox` 取词坐标；框线围成网格，缺内框即合并格，词按中心归格。
- 模板文字仍逐字保存，表格只是附加的结构；对不上或已被人工改动的文字照原样输出。
- 真实运行里修过的问题：双线或粗边框被识别成两条线（合并间距小于 4 磅的线）；同页两张表并成一张（按框线连通关系分表）；页面装饰线凑成空框（原文行须属于单元格文字才算，整表对不上即丢弃）；跨页续表。

### 5.10 环境一致

几次“本机好、线上坏”都是环境问题，不是逻辑问题：

- poppler 版本不同导致表格线解析结果不同，底座统一后消失。
- 远程主机上 Worker 外层沙箱里再起 Codex 内层沙箱，无法挂载 `/proc`，表现为 `OUTLINE_ARTIFACT_MISSING`、`OUTLINE_REPAIR_NO_PROGRESS`；需在远程设 `CHAPTER_TEMPLATE_BWRAP_DISABLE=1`（远程结果尚未回报）。
- 宿主机 Python 3.6 导致一批桩测试失败。
- 部署的 Worker 不含本地修复时，线上任务不能作为修复证据（2026-11-06 就出现过）。

## 6. 踩过的坑

- **在提示词里堆规则。** 规则互相打架，模型挑一条执行；修一个样例坏另一个。安服样本里一句“整体填写的表样输出空数组”让模型把整章采购需求都不展开。
- **让模型输出长 JSON。** 截断、Schema 不合法、两次结果不一致；写和回读工作稿本身占了大量时间。
- **读取截断没被发现。** 工具输出超限被截断，模型以为读完了并声明读取完成。现在由运行层记录截断和未续读的游标，交付声明不能覆盖实际读取缺口。
- **分页游标被跨字段误清。** 接收核对读索引返回了续读偏移，后续读取元数据却显示空游标，结果只读了第一批。
- **逐片审查 + 多轮修复。** 每轮都可能改坏已正确的部分，轮数和耗时不可控。正文响应的评审—修正循环曾无上限，一章停了 3 小时。
- **兜底路径被后面的校验反杀。** 给循环加了上限后，上限兜底产出的结果又被确定性校验判为非法，47 章失败。加兜底时要连同下游校验一起看。
- **会话内检查通过、交稿后宿主另报错。** 模型能用的检查和宿主最终检查不一致，白跑一轮。两边要用同一套检查。
- **会话用量重复累计。** 同一会话多轮的累计值被相加，统计翻倍。
- **内部限额做成环境变量。** 部署漏配就直接失败，现在改为带说明的常量。
- **一个大步骤失败就整轮失败。** 用户等了半小时什么都拿不到。
- **历史数据结构变了没人管读取。** 大纲字段从字符串改成结构后，旧项目的页面和接口直接 500。
- **只读一处记录就下结论。** 曾只看进度文件，误判“没有自动比对”，还重复起草了一份与现有夹具有出入的目录标准。
- **文档跟不上代码。** `outline-generation-flow.md` 的文件表里还列着已删除的来源片提示词，改 agent 驱动前应先更新。

## 7. 工程方法上的经验

- **先测再定方案。** 2026-11-10 的方向是靠一组小实验定的：直连可行性、单次目录稳定性、双读裁定、计划改直连、参数展开。每个实验半天内出结论，没通过的直接放弃，没有写进生产代码。
- **冻结验收口径。** 目录标准在 `scripts/tests/outline_directory_cases/`，比对脚本 `scripts/verify_outline_directory.py`，结果分目录、模板、参数、章节要求四类计数。
- **夹具只在评估侧。** 不进生成输入，业务代码和提示词不写样例内容；222 留作未调优样本。
- **稳定性要多次跑。** 同一文件至少 3 次，看差异数和树是否一致。单次通过不算。
- **记录分清已证实和假设。** `fix-bug.md` 里每条写明证据来自哪里、哪些没验证；工程检查通过不等于业务通过。
- **做减法。** 稳定是删出来的：接收核对、来源片、结构纠正、最终复核、选名字段都删了，对应测试一并删。
- **新样本会暴露新问题。** 安服没有夹具，第一次跑就发现展开提示的缺陷和根章节取名不固定。夹具覆盖范围内全绿不代表泛化。

## 8. 改成 agent 驱动时的建议

第一阶段的经验可以归结为一句：**agent 负责判断和定位，程序负责搬运、编译和校验。** 按这个分工扩展，而不是把现有程序步骤都换成 agent。

1. **保留“只定位不抄写”。** agent 的交付物是位置和决定（哪一页哪几行、采用哪份清单、这是章节还是内容），不是成品文字。给 agent 的工具应该是“读某页”“按行号取原文”“提交计划”，而不是“写大纲”。
2. **保留宿主编译。** 目录的父子、顺序、编号、命名规则继续由程序算；agent 改的是计划，不是结果。
3. **agent 只用在需要来回翻原件的地方。** 目录属于这类。输入范围已确定的环节（参数展开、章节要求）直连更快更稳；改成 agent 之前先用夹具对比，没有提升就不换。
4. **agent 的检查和最终检查用同一套。** 让 agent 在会话里就能调用宿主检查并看到具体错误，避免交稿后才被拦。
5. **目标要窄，写成可检查的三五条。** 不要给 agent “把所有要求都归对”这种没有原文可对照的目标。
6. **失败单位要小。** 每步独立缓存、独立重试，失败转待确认；多个 agent 之间靠已保存的结果交接，不共享长会话状态。
7. **控制代理循环的成本。** 现在目录单步 35 到 43 次往返、上百万输入 token。可以试的方向（假设，未验证）：预先给 agent 一份程序算好的标题候选和组成清单位置，减少翻页次数；工作稿改为增量提交，避免反复整份写入和回读。
8. **两份独立结果对照可以继续用**，并补上“按差异选更完整的一份”的规则；同时记住它发现不了共同漏项。
9. **循环必须有上限，上限兜底必须能通过下游校验。**
10. **每次改动都用同一套夹具比对。** Bid、111、安服做回归，222 留出。改之前先记下当前基线（差异数、耗时、三次是否一致）。
11. **先统一运行环境再比结果。** 沙箱、poppler、OCR、Python 版本在开发机和 Worker 上保持一致；确认线上跑的是含修复的版本。
12. **不为提速删复核。** 提速只在目录之后的环节做。

建议的迁移顺序（假设，供讨论）：先把现有流程的每一步封装成 agent 可调用的工具并保持结果不变，用夹具确认 0 差异；再逐步把调度权交给 agent；最后才考虑让 agent 接管更多判断。

## 9. 尚未解决

- 两份目录计划固定采用第一份，可能选中有缺项的那份。
- 原文自身名称矛盾时（安服三处写法不一），根章节采用哪一方两次运行不固定，只是都写入了待确认。
- 同项目多份招标文件（补遗、答疑）之间的效力关系未验证。
- 不足 25 行未展开的参数表、无框线表、Word 原件表格没有单元格结构，逐章记入待确认。
- 表格竖线端点越界可能产生空行（未实测）。
- 直连缓存不区分任务，同一文件重新解析会复用上次回答。
- 远程环境沙箱开关设置后的结果尚未确认。
- `outline-generation-flow.md` 已过时。
