# 招标解析之后的一次大纲

运行时见 [大纲运行时](outline.md)。一次成稿是产品路径上的发现、组织、核对和完成。发现之后，组织同时写章节、附件绑定和规定模板槽。106 页真实招标 PDF 的发布记录和还开着的项见 [大纲计划](../../plans/bidding/outline-gaps.md)。

## 用户流程

1. 上传招标文件并等待解析完成。解析未完成时不能生成大纲。解析完成也不会自动开跑。
2. 用户点击生成大纲。一次运行依次做完发现、组织（章节、绑定和规定模板槽）和收尾，得到冻结的 `OutlineArtifact`。
3. 之后由 `response` 做知识库填充：只读这份冻结大纲，把投标人槽和签字槽填上证据或标成待人工补充。这一步不是 `DraftStage::Fill` 上的模板职责。`response` 不重新解析招标文件，不改章节，不改规定文字。
4. 用户在 ONLYOFFICE 中改已保存的投标文件，保存后下载。需要 PDF 时由 ONLYOFFICE 从同一份已保存 DOCX 转换。正文编辑器只有 ONLYOFFICE。

没有草稿编制和正式编制两条生成流，也没有强制终稿复核才能下载。

## 一次大纲里的三步

| 步骤 | 做什么 | 不做什么 |
| --- | --- | --- |
| 发现 | 按章节边界领取阅读包。应答义务是投标人必须提交、填写、声明、承诺、报价、列偏差、提供资格证明或按指定格式作答的事项。读完该包再提交；没有这类事项时交空数组。同一包失败后按字段错误再交 | 不写章节，不写模板，不查知识库 |
| 组织 | 写出章节树，每个附件表只绑定一个章节，并用 `put_slots` 写入招标文件已经给出的文字。有两张及以上互不续表的附件表时，树要有三层：根分组（可多个，即森林）、中间分组、叶子应答。中间分组沿用招标文件自己的章节，不要为每一张附件表设一个应答章。同一条续表链只绑一个叶子；互不续表的附件表可以绑在同一个应答章。每个应答章节至少有一个槽。投标人槽和签字槽留空，并带 `match_query`。分组章节不能带这两种槽。缺槽、树太扁或一条链拆到多章时留在组织 | 不重新领取阅读包，不填写我方报价、资质、人员或证书 |
| 收尾 | 每个应答章节都已经有槽之后，阶段是 `check`。`readiness.next` 是 `finish_outline`。`finish_outline` 被拒绝则回到组织，不在收尾里重试 | 不改章节，不改槽，不重新扫描 |

章节用途只有两种：`group` 容纳子章节，`ChapterPurpose::Response` 是投标人作答的章节。分组章节不能带知识库响应槽。这个用途和包名 `response` 不是一回事。

## 三个包

| 包 | 产出 | 边界 |
| --- | --- | --- |
| `analysis` | 对冻结招标文件的记录、关系和修复 | 不发布章节，不写模板 |
| `outline` | 章节树、附件绑定、规定模板槽，收尾后成为 `OutlineArtifact` | 不评审分析记录，不匹配知识库。生成合同以这个包为准 |
| `response` | 按冻结大纲上的响应槽填写知识库证据 | 不解析招标文件，不改章节，不改模板。没有证据的槽保持 `【待人工补充】` |

`OutlineArtifact` 带项目身份和冻结输入摘要。响应结果用大纲摘要绑回这一份，不能绑到另一轮大纲。

## 记忆

不保留一份随运行增长的语义记忆。能恢复的状态在检查点里：发现进度、工具草稿和阶段。会话只复用当前窗口里的模型对话。
