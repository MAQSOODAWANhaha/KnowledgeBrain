## 结论

**当前直接失败点是 Agent 未把已经具备条件的局部工作执行完，运行层又允许相同工作状态持续查询。** 这是业务任务推进与恢复策略的缺口。正文定位、上下文裁剪确实影响过运行，但不能再把本次零关系简单归因为“关系两端装不下”或“工具写不进去”。

模型内部为什么持续选择查询，无法从 Chat 轨迹证明。以下区分可复现的工程事实、已排除的假设和需要后续真实对照验证的措施；不声称已找到一条能保证模型改正的提示词。

## 代码层的缺口

### 1. 有界请求没有同时形成可核查的局部任务

`tender_analysis/agent/context.rs::WorkState` 保存来源 UUID 范围、自由文本目标、已有成果引用、未解决成果引用和笔记。当前范围有3个来源、28条相关记录，目标同时覆盖两页条款、前附表关系及外部条款引用。

Agent 可以在目标文字中选择小任务，但程序不知道它当前要完成哪一组比较、哪一条关系，以及哪个外部引用可以留待后续。`pending_refs` 记录的是已经保存的未解决成果，不是未完成动作的通用列表；需要先保存相应未解决记录再纳入待办。局部动作顺序与检查结果都依赖模型主动维护自由文本及引用列表。

本次模型已保存15条新记录，但没有把14条普通成果和1条未解决记录加入工作交接。上述17项缺口存在且可见，却没有促成一次局部完成。这说明当前措施保证了“未交接不能冒充完成”，尚未保证“Agent 能走到交接”。

### 2. 运行循环区分了协议成功，没有处理任务长期不前进

`agent_runtime/driver.rs::drive` 检查取消、总预算、合法工具轮次、预约和持久化，然后继续。`tender_analysis/agent.rs::RunDriver::status` 以轮数、工具次数、累计读字节控制预算。

反复成功查询会增长这些计数，但不会改变候选版本、关系、来源处置或交接状态。现有循环缺少对这种状态的有界恢复分支。因此协议和 Journal 都能正常工作，任务仍能重复到总预算耗尽。SDK 多轮驱动正常并不等于业务规划正常。

### 3. 历史裁剪存在加重重复读取的条件，但不是本次唯一原因

`inspect_in_context` 检查取回候选后是否还保留原文证据；它调用的 `visible_work_evidence` 清点正文、网格和图片，不清点完整候选版本。

`evict_delivered_group` 也用这一清单判断组是否可替代。因此仅包含候选详情的旧工具组，在这项“来源证据冗余”判定中可能是空集；它并未证明该组的候选详情已由其他组覆盖。这使当前比较所需详情缺少独立保护。

但是，实际轨迹中四组双方多次同时可见仍未写入，说明只修这项裁剪不足以宣称解决停滞。也不能把所有候选详情永久保留：上下文仍必须有界。需要先明确当前比较对象，再保护该对象所需的证据与详情。

## 建议的最小修复顺序

1. **先补局部任务的推进约束，沿用现有 WorkState。** 由 Agent 选择当前条款或比较对象的真实引用；一次处理一项可完成的比较/关系，并保存结果。跨范围未知目标先登记已有未解决成果，再处理当前可完成项。来源 UUID 范围继续控制读取权限，局部焦点表达本次比较对象，两者职责分开。无需新增 Agent 表或第二套队列。
2. **加入基于实际状态的停滞识别与有界重新规划。** 依据新增已交付来源覆盖、成果/关系版本、来源处置及有效工作交接判断进展；查询次数、重复读字节、改写一句笔记不算成果进展。触发后提供具体未变化状态，让 Agent 选择下一项局部动作；恢复仍无效则保存检查点并明确停止。阈值通过统一配置提供默认值，不把本次28轮或样稿编号写入业务规则。停止机制控制损耗，本身不是提取质量修复。
3. **围绕当前局部焦点调整候选保留。** 只保护当前比较所需的两端/相关对象及原文证据，区分完整候选版本和导航结果；保留现有完整协议组、待交付结果及阅读回执约束。不要在缺少焦点时把所有历史详情都当成永久证据。

优先验证业务调度，保持当前 Rig 0.42.0、Chat、统一 Python 解析及 `.env` 模型配置。此证据不支持立即更换 SDK、替换模型或扩大预算作为确定修复。

### 重复读取导致的交接阻塞

`response-contract-trial` 第23–26轮多次在读取已有详情或目录后执行 `check_gaps scope=work`，得到唯一的 `pending_delivery`；下一请求基于已交付内容的工作清单却无缺口。原实现只检查 `pending_coverage.is_some()`，重复读取也会触发，诱使模型再次读取后继续等待。现删除这一冗余条件，完成仍使用已确认的原文覆盖和本角色当前候选摘要；同批新读但尚未交付的内容不能消除真实缺口。双角色重复读取交接回归与未交付证据拒绝回归通过，未改变工具/提示词/预算或Journal形状，以同一检查点兼容恢复。

### 独立复核读取完成后仍不提交

兼容恢复 `response-contract-resume1` 主提取完成了41条记录、21条关系和3项来源处置。reviewer 收到65个候选当前版本、全部原文/网格及3张原页后，工作缺口清单已为空，仍反复声称要读取剩余对象；两次重规划后进入阻塞，于第101轮耗尽独立工作交接窗口，0轮复核。终态见[实跑结果](../../artifacts/bid-full-sample/loop-repair/response-contract-resume1/result.json)。

`submit_review` 原本就允许完成核查后提交空发现列表，不能诊断为缺少接口。可确认的反馈缺口是：主/复核共用“写出结果”的恢复语句，空工作清单只给出空集合，未明确切换到比较和完成。现动态反馈区分角色及真实缺口，明确保存问题、无问题完成原范围、处理待办后提交三个动作；程序不自动产生发现、批准候选或清除阻塞。回归验证独立阅读不被反馈替代、另一角色的阻塞不能被空清单掩盖。这个改动改善完成指引，不能仅凭测试断言模型会遵守；提示词合同变化后以新身份做真实对照，不重置已失败运行。

离线检查该 reviewer 的32个实际请求，其中13个请求存在完整候选及其所引正文/网格共同可见的窗口（如第94轮24条记录与两页全文、48格网格同在）。因此不能把全部停滞归为“从未同时看到候选和证据”；这也不能证明图片判读或语义比较已完成。见[窗口核查](../../artifacts/bid-full-sample/loop-repair/response-contract-resume1/reviewer-context-observation.json)。

### 待处理未决记录污染局部复核缺口

`reviewer-completion-trial` 的 reviewer 首先选择前附表来源，将两页正文列为 deferred_sources。`retain_outcomes` 正确保留了全部待办，但 `scoped_gaps` 随后把所有 prior.pending_refs 都作为当前完成前必须独立取回的对象，包括仅属于待处理正文的未决记录。保留待办不应强迫每个局部范围重复承担不相关的复核任务。现局部检查仅列当前来源及其相关关系，其他待办继续保存在 WorkState，由后续范围和最终全局独立复核门槛处理。两来源回归先验证当前范围可完成、未读待处理来源仍禁止提交，再独立读取待处理来源和候选后完成提交；未决记录保留。

同一次实跑还暴露读取工具把中文字符内部起点、越界和零长度统称为 invalid UTF-8 range。现在反馈准确字段、错误字节以及相邻合法边界，读取起点不自动纠正，错误读取不建立回执。两项都不改变工具、提示词、预算或Journal合同，可在旧预约原文保持不变的前提下兼容恢复。175项库测试、20项合同及Clippy/格式/编译通过。

### 无问题的局部核对结果

完成指引使 reviewer 完成过一个局部范围，但第79轮已收到全部72个候选后仍反复读取，于第85轮到诊断时限，0轮最终复核。不能声称提示词已解决停滞。已有 put_review_finding 可持久化错误，缺少与之对应的单个候选无问题比较结果；整个来源范围的 complete 不能记录范围内逐项完成。现 complete_review_check 要求活动复核焦点、当前候选的独立详情回执、原文证据及比较说明，用候选引用和版本摘要生成唯一进展记录。改写说明、更换引用区间或重启不能重复计入同一候选版本；候选修改后需重新独立取回。已有问题不能被无问题声明覆盖，局部结果不是自动批准。复用进展账本与 Journal 工具历史，无新表、检查点字段或 migration。

新增样稿程序 review 模式把归档主提取候选绑定为独立诊断输入：seed 摘要加入运行合同、reviewer 从空覆盖开始、旧运行及其计数不变，输出为 review-diagnostic-result.json，不能冒充新的完整提取样稿。176项库测试、20项合同及Clippy/格式/编译通过。新身份[诊断清单](../../artifacts/bid-full-sample/loop-repair/clean-review-trial/start.json)已获补充明确授权并执行；此前自动审批拒绝保留为历史记录，真实终态见下节，最终复核未完成。
