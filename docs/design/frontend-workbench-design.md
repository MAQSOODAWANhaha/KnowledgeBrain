# 投标编制工作台交互方案

## 核心决定

正式标书直接在 ONLYOFFICE 中展示和编辑 DOCX。网页承载文件导航、招标要求、采用依据、
待补事项和执行状态，正文只有一个正式编辑入口。

产品保留“投标项目 / 知识资产”两大入口。项目内按“项目资料 / 招标解读 / 标书编制 /
交付文件”组织导航；各分区可自由切换，不增加人工审批节点。

外壳的颜色、几何、分区滚动和动效只以 [DESIGN.md](../../DESIGN.md) 为准。离线 HTML 草图已删除。本文只保留稿件、保存、定位和编制行为。

## 页面行为

- 左右侧栏均可收起。窄屏右栏改为抽屉，优先保留稿件空间。抽屉的位置跟着编制区，不写死距离视口顶部的像素。
- 打开稿件后默认阅读，进入编辑时仍操作同一份 DOCX；不设置独立网页正文视图。
- 工具栏明确区分当前查看的稿件、已保存版本、编辑中的修改及后台生成任务。
- 页面操作使用“生成新稿”“保存修改”“下载已保存稿”，不要求额外点击“同步到 Word”。

## 文件形成前后

| 情形 | 中间区域 | 目录与右侧信息 |
| --- | --- | --- |
| 首次生成，尚无 DOCX | 显示实际执行阶段、已形成的大纲及明确的等待或失败原因 | 展示已可读取的结构、要求和问题；未知内容保持未知 |
| 已有 DOCX | 直接打开该版本的真实稿件 | 展示对应版本的目录及已绑定的要求、依据、缺口 |
| 已有稿件，后台生成另一稿 | 保持当前稿件可读、可编辑 | 提示后台任务进度，不因任务更新重载编辑器 |
| 新稿已形成 | 提示“查看新稿 / 继续当前稿” | 用户选择查看且当前修改处理妥当后，才切换稿件 |
| Word 服务暂不可用 | 显示重试入口及最后已保存稿的下载入口 | 保留已读取的项目和业务信息 |

执行进度来自已保存的实际状态和回执，不伪造百分比；仅在确有产物时展示正文或文件。
任务失败、文件已形成、资料待补和内容待核对分别表达，不能合为一个“完成”状态。

## 目录与业务定位

左侧展示分册、章节、表单及附件位置。点击目录定位当前 Word 稿件，同时切换右侧信息；
点击待补事项定位对应响应位置。首版右栏跟随左侧选定章节，并清楚标示该章节名称。

正式接入需要把章节及响应位置的稳定身份写入 Word 锚点，并绑定具体稿件版本。不能只
按标题文字匹配；重名、改名、移动及删除章节均须验证。锚点缺失或已删除时明确提示
“位置需要重新关联”，保留要求与问题，不跳到相似标题冒充成功定位。

编制页提供“大纲编排 / 正文编辑”两个视图。生成正文前，可在网页大纲中新增、重命名、
删除章节，调整顺序和层级；新增章可填写编写说明，否则只保留标题。大纲保存为不可变修订，
用户显式按该修订生成正文。生成后，当前稿件的标题、顺序和正文仍可在 Word 中修改；
服务端确认保存后，从实际 DOCX 更新目录与位置映射。网页大纲修订用于下一份生成稿，
不会直接重排正在编辑的 Word。人工新增位置不能自动认定已绑定某项招标要求。

目录切换与展开业务侧栏应保持编辑器和未保存修改。Word 内光标变化驱动右栏属于需单独
验证的联动，不作为首版已经具备的能力。

## 保存、下载与新稿

1. 修改发生后显示“有未保存修改”。修改已发送到编辑服务与已保存到平台是不同事实。
2. 点击保存后显示“保存中”；服务端确认保存回执与本次会话、父版本、结果版本及文件
   身份一致后，才显示“已保存”。
3. 网络中断或回执未知显示“保存结果待确认”，确认同一次请求；明确保存失败时保留
   编辑现场并提供重试，不清除修改标记。
4. 下载使用明确的已保存版本，按钮或相邻文案标出版本。存在未保存修改时说明下载稿
   尚未包含这些修改；DOCX 下载不依赖资料齐备或问题全部关闭。
5. 生成新稿使用固定资料快照和明确更新范围，保留原稿及人工修改。首版不承诺把人工
   Word 修改自动合并到 AI 新稿，也不把手工改稿自动回写为已核验的结构化编制结果。
6. 切换稿件、离开编辑页或结束会话前，处理未保存修改及未知保存结果；后台新稿就绪
   只通知，不自动替换正在编辑的文件。

## 右侧要求、依据与待补

- 要求显示原文、适用范围、条件及来源定位，章节存在不表示已充分响应。
- 依据区区分招标原文、企业资料和真实证明原件；资料命中不等于适用或满足要求。
- 待补项说明缺什么、影响哪里和可采取的补充动作；人工报价保留对应原表空位。
- 复核意见标明依据的稿件版本。人工补写内容后，原意见保留为待核对，不自动清除。
- 缺企业资料、分析未确认或仍有待补事项时，继续提供已有稿件的阅读、保存与下载。

## 接入边界

现有 [Word 组件](../../web/src/bid/authoring/DocxEditor.tsx)及
[保存会话逻辑](../../web/src/bid/authoring/docxSession.ts)可用于适配参考；
Python [编制执行入口](../../services/docreader/tender/document_execution.py)及
[导出器](../../services/docreader/tender/authoring_export.py)提供编制产物。
落地需要贯通项目权限、后台执行、文件读取、编辑保存、版本保护和下载接口。

章节锚点、编辑器外部定位以及保存后的目录更新需要独立验证。实现方式须适配实际
ONLYOFFICE 部署版本，不默认依赖 Developer 版专属的 Automation API。

页面查看、目录切换、保存和下载使用宿主能力，新增模型调用为零。编制调用仍遵循现有
Python 合同，只有显式编制或复核动作才触发对应执行；页面轮询、刷新和恢复查询不能
重复创建付费任务。

业务语义以 [Python 业务流程](python-tender-phase1/business-workflow.md)及
[字段字典](python-tender-phase1/field-dictionary.md)为准。

## 实施与验收顺序

1. **同版稿件读取与下载**：从真实编制成果进入 Word；验证版本、权限及文件对应一致，
   无资料或有待补时仍能读取和下载。
2. **编辑保存与保护人工稿**：验证修改、保存、回执未知、失败恢复及离开提示；服务端
   确认前不显示已保存，新任务不抢占编辑器。
3. **目录及问题定位**：补稳定锚点与保存后目录更新，验证重名、改名、移动、删除和
   人工新增章节；关联失效有明确提示，不猜测绑定。
4. **新稿切换与业务复核**：验证后台新稿仅通知、显式切换、历史稿保留、复核版本标注，
   不以人工写入文字或文件生成成功代替语义核对完成。

## 大纲编排与版本边界

独立“生成大纲”只运行现有原文组织与全局归并，结果作为候选；后台完成不替换已保存
大纲或本地未保存修改。用户可查看候选、编辑并保存，保存绑定父修订与具体来源，
并发冲突保留输入并提供重新载入；结果未知时重试同一保存请求，不偷偷采用最新修订。

大纲树支持新增同级/子级、改名、删除、上移下移、缩进提升和拖拽。删除章会同时移出其
响应位置，界面须明确影响；原招标规则及未安排问题保留。原位置的表单、附件和来源引用
由服务端按稳定身份继承，网页不修改这些正式引用，也不推断新标题已经满足要求。

“按大纲生成正文”只使用平台已经确认保存的具体修订与摘要。任务提交结果未知时，
恢复仍使用原请求中的修订；草稿后来变化不改变该任务输入。资料已更新时，明确提示
重新生成大纲，原修订和 Word 仍可查看。资料缺口或分析未确认不增加审批节点。

两视图各自保留选择和修改状态，切换视图保留已有 Office 实例。离开项目时同时保护
未保存的大纲及 Word 修改。大纲保存状态、Word 保存状态和后台任务进度分别表达；
后台 Word 新稿仍作为候选保留，由用户安全关闭当前编辑会话后显式切换。

正文编辑区保留至少420px，包含Office菜单后仍有可操作的正文空间；高度不足时工作区
纵向滚动。窄屏核对抽屉将标题和关闭按钮一并放在抽屉内，缩放窗口后仍可关闭并操作Word。

离线草图、接口合同测试、真实 ONLYOFFICE 保存测试以及真实招标文件验收分别报告。

历史大纲可读取、预览与当前同标识章节对照，再显式载入另存修订；空历史也能另存。
响应安排列出当前及未安排响应，用户将原响应迁至选定章，完整要求/来源/原表由服务端
保留。目录尚未读取时明确显示未知，不以0项掩盖读取失败；历史与响应目录独立重试。

项目资料页可显式选择知识资产固定版本，提交正文时冻结选择；后台不保存用户登录令牌。
招标解读页可逐项记录人工判定，纠正文案、条件、例外、量化事实、评分、后果及提交
字段后重新审核；完整事项与冻结原文依据一起保存。人工输入、未知请求和Word/大纲状态
均纳入离开保护，提供显式放弃。
