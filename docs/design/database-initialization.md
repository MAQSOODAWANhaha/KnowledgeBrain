# 数据库初始化与业务归属

本次结构重设计从全新数据库开始，不兼容旧业务数据，也不重置现有数据库。新库初始化与后续增量升级统一使用 SQLx 版本迁移；“无需兼容旧数据”不代表取消以后的升级能力。运行服务不再创建或升级业务表。

## 版本迁移

`migrations/` 是业务 DDL 的唯一来源，文件使用 UTC 时间戳加业务说明，按版本递增执行：

```text
20261028000001_shared_platform.sql
20261028000002_knowledge_base.sql
20261028000003_tender.sql
```

沿用现有 `migrator` 二进制和 Compose `migrate` 服务，内部使用项目已有 SQLx 的标准迁移器，编译时嵌入 SQL，并跟踪目录新增文件。SQLx 的 `_sqlx_migrations` 记录版本、说明、校验和、成功状态和执行耗时；它是工具内部表，不套用业务域前缀。

- 首次启动按顺序执行所有文件；后续启动校验已执行文件，只运行未执行版本。每份 SQL 和对应台账在同一事务提交，并通过 SQLx 的数据库锁串行执行。
- 单份 SQL 失败时回滚该文件，之前成功的版本保留。修正尚未成功发布的文件后重试；已经应用的文件不可修改、重命名或删除，结构变化新增时间戳 SQL。不要重写校验和或清迁移记录来绕过错误。
- 不额外扫描或要求整个 `public` schema 为空。SQLx 管理迁移记录，普通 `CREATE TABLE/DOMAIN` 遇到同名对象即失败；该文件内的变更回滚，不覆盖既有对象。不相关且名称不冲突的对象可保留，不自动接管旧业务结构。
- 发布顺序仍为数据库就绪 → `migrator` 成功 → Python checkpoint 初始化 → API/worker/dispatcher。应用进程只检查/使用结构，不自动补表。
- 新增迁移可使用 `sqlx migrate add <业务说明>`，执行可用 `cargo run -p platform --bin migrator`；已正确配置 `DATABASE_URL` 的开发环境也可用 `sqlx migrate run` 和 `sqlx migrate info`。生产继续由已有发布入口执行，不新增 CLI 或配置项。
- 默认只做前向迁移；失败事务回滚与生产数据回退不是同一件事，不自动生成可能丢数据的 down 脚本。

验收使用专用测试库覆盖首次建库、台账、重复执行保留数据、追加增量、失败回滚后恢复、已执行 SQL 校验和变化和并发执行，并验证无关表不阻塞迁移、同名冲突正常报错且原数据保留。不实现旧库接管或清库；每份迁移独立提交，后续文件失败不会回滚此前已成功的迁移。

## 业务权限

统一规则是“谁创建、谁可见、谁可操作”。知识库以 knowledge_workspaces.owner_user_id 为归属根，产品、版本、资料、标签、检索与派生产物继承该归属；投标项目以 tender_projects.owner_user_id 为归属根。列表和详情、写入、下载、检索均在业务层检查归属。用户不能把其他人的资源 ID 作为关联对象绕过校验。

API Key 绑定创建用户（owner_user_id），作为该用户的认证凭据，不再有 workspace/product scope 或 read/write 分级。它可操作所属用户的全部业务资源，不可跨用户访问。取消 Owner/Admin/Contributor/Viewer 成员模型。全局服务配置和运维操作仍属于部署管理员职责，普通资源创建权不等于服务管理权。Bootstrap 凭据对应配置的管理员用户，不绕过资源归属。

不保留操作者字符串或身份DOMAIN。未绑定业务实体的上传暂存直接保存 `owner_user_id uuid`，登录和Key使用同一用户身份；内部后台上传可为空，但空值不能操作属于用户的上传。招标文件及对象引用沿项目/业务实体继承归属，不冗余保存用户owner。审计、维护及删除回执移除未使用的操作者列，保留原有事件和生命周期记录。

## 存储职责

表、字段和关系采用 [数据库命名与关联约定](database-naming.md) 的精确映射。数据库内部统一业务域前缀，通过读写适配保留外部 HTTP/gRPC、模型、队列与 CAS 合同；不增加兼容视图或双写。

| 领域 | 保留的数据 | 调整 |
| --- | --- | --- |
| 平台 | 用户、Key、对象登记/引用、上传暂存、删除任务、删除回执、必要审计及维护状态 | 对象生命周期由 Rust 事务处理，删除未使用的幂等合同/队列合同/维护审计结构 |
| 知识库 | 资料层级、解析结果、模型与检索配置、索引代次、任务 outbox/回执、已有 Wiki/Graph | 删除成员角色、遗留匹配认证接口和冗余不可变性过程；不删除实际业务能力 |
| 招标 | 项目/文件、Python 分析运行/修订/命令/产物/确认/调用回执、编制执行/调用回执、Web 调度、Word 编辑版本/会话/保存/恢复 | 统一 baseline，退出旧 Rust 招标运行入口和对应旧表/发布过程，合并 Word 增量初始化入口 |

数据库保留 PK/FK、唯一约束、简单 CHECK、索引和事务锁。不设置业务角色、RLS 或 SECURITY DEFINER 授权入口。平台、知识库与招标均不定义自定义数据库函数或触发器。索引计算、任务投递、代次隔离及派生数据失效由 Rust 服务显式执行，并与对应记录变更置于同一事务。PostgreSQL/pgvector 自带函数与扩展不属于业务存储过程。

对象引用登记/释放、上传暂存提交、最后引用删除任务必须保持同一事务与对象行锁。知识库解析的 outbox、attempt/generation 围栏、索引发布和派生数据失效必须完整保留。Python 的付费回执、幂等、租约、同修订重试、编辑版本并发均不因简化数据库授权而删除。

## 实施与验证

1. 重写三份初始版本迁移，统一 Python 表结构来源；验证单文件事务、迁移台账、增量升级、重复执行行为和实际目录对象。
2. 同步替换函数调用与服务启动检查；验证对象暂存/引用/清理、上传投递、索引、分析与编制回执、Word 保存恢复。
3. 统一服务层归属检查和 API Key；用两个用户验证列表、详情、写入、检索、下载与跨资源关联隔离。
4. 仅使用独立测试数据库；明确区分静态/隔离检查与真实招标模型验收，本次数据库重构不需要重新付费调用模型。

本次不改变模型协议、分包或 Prompt。全文件模型调用数、单请求输入输出和修订重跑量均保持原方案；不新增模型誊写或语义门禁。迁移失败回滚当前文件并允许修正后从未完成版本继续，业务事务失败沿用现有任务重试出口。
