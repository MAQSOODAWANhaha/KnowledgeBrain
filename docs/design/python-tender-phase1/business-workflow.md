# 第一阶段业务工作流：完整分析招标文件

## 目标、范围与当前状态

**输入完整招标文件及附件、澄清、补遗，输出经过核验、可追溯的招标事项台账。**
本阶段分析招标文件规定了什么，包括评分标准、资格条件、否决条件及其他业务要求。
原文明示的填表字段、证明材料、方案应包含的内容、签章和提交要求均属于分析范围。

企业响应数据、材料准备待办、响应动作、响应计划、加分取舍、实际得分、投标正文生成和
最终导出不在本阶段。输入缺少企业证书或实际人员资料，不构成招标文件分析的来源缺口；
缺少招标文件引用且理解规则必需的附件，则必须记录并阻断完整分析。

本文规定流程，所有字段、类型、可选性和枚举以[唯一字段字典](field-dictionary.md)的目标 v2 为准。
**五节点、新事项协议和 `analysis-ready` 已实现并部署；完整真实语义验收尚未完成。**
新入口确认后结束分析，不再推进旧Plan；旧运行记录及独立工具保留原义。
运行、测试及部署事实统一见[交接](handoff.md)，本文不重复维护实时包数。
下一修订的优化方案见[问题全量复审](bug-fix.md#全量根因复审与统一优化方案)，
拟新增字段只在字段字典的设计章节定义，不属于当前已部署合同。

## 分析范围由来源决定

下列内容用于阅读和查漏，允许交叉，不是固定节点或封闭业务枚举；原文没有的内容不补造。
项目身份、标段、采购对象和文件版本作为来源上下文保留，说明性文字不强行转成义务。

| 内容 | 需要保留的来源信息 |
| --- | --- |
| 资格及实质性条件 | 企业/人员资格、资质、业绩、信用、联合体及适用条件 |
| 评分标准 | 对象、指标层级、分档、公式、加扣分、分值/上限、计分条件和证明要求 |
| 否决及其他后果 | 触发条件、作用范围，区分否决、无效、不得参与、扣分、不得分和履约责任 |
| 技术及方案 | 参数、性能、标准、方案内容、实施措施、测试及证明要求 |
| 交付及验收 | 范围、数量、进度、交付物、验收方法及条件 |
| 服务及售后 | 响应/到场时限、维护、培训、保修、备件及例外 |
| 人员及组织 | 角色、数量、资格、经验、在岗要求及原文明示的人员信息字段 |
| 商务及报价 | 价格组成、税费、支付、保证金、有效期、合同及履约条件 |
| 文件及提交 | 内容、格式、表格字段、附件、签章、份数、提交方式、期限和程序要求 |
| 适用范围与修改 | 标段、主体、条件、例外、跨章引用、澄清及补遗的具体修改范围 |

例如“人员表填写姓名、证书编号并附证书”须完整收录，但不填写实际姓名或生成收集证书的待办。
“持 B 证加 2 分”须收录规则及证明要求，不决定是否争取、不预测企业得分。

## 五个主节点与放行条件

**登记文档集 → 解析冻结 → 统一分析 → 独立核验 → 人工确认 → `analysis-ready`**

| 节点 | 输入与产物 | 放行条件 |
| --- | --- | --- |
| `register` 登记 | 主件、附件、澄清/补遗的身份、版本、角色及已声明关联；来源清单和缺件问题 | 原件已持久保存、身份可追溯；缺件不能悄悄排除 |
| `freeze` 解析冻结 | 规范正文、章节、表格/合并关系、实际图片 OCR、附件位置、可用性目录及解析缺口 | 可读范围可先完成；必要来源缺口保留，不允许最终确认 |
| `extract` 统一分析 | 带必要上下文的小批原文；输出统一事项、逐范围处置、候选关联和未决引用 | 宿主组织完整逐范围处置；局部回包缺陷保留有效结果和待核对问题继续 Verify，不把本包不可见判成全文缺失 |
| `verify` 独立核验 | 冻结来源和抽取事项，按[核验规则](#核验怎么发)重新预算分批 | 依[状态规则](#状态修订与恢复)区分硬阻断和人工确认；缺页或漏报原子不触发额外模型轮次 |
| `confirm` 人工确认 | 展示来源、事项、评分/后果规则、关联及问题，逐条处理剩余语义疑点并确认当前版本摘要 | 无硬阻断、每个语义疑点均有驳回或保留的人工结论、确认与当前来源/领域修订及核验结果一致，提交确认回执后进入 analysis-ready。硬阻断只阻止这一次确认，不阻止编制读取当前快照或导出 |

结果视图由来源、事项、核验产物及确认回执组装，不增加报告生成 LLM 节点。
无需为人员、评分、技术等分别建立 Agent，也不引入主 Agent 自由选择后续工作流。
阶段内只发这一次 review。没有已知问题也不另开跨源发现轮。

模型负责事项、证据选择及业务关系的含义；代码负责身份、原文定位、反向引用、分包、
预算、存储和推进流程。可恢复引文、冗余索引和可选数字细节不完整只记宿主诊断，
不使整包失败；无法追溯的声明交给独立核验，不由代码推断业务或静默删除。
具体容错边界统一见[字段字典](field-dictionary.md#回包容错与继续核验)。

## 当前发送边界

冻结原文是唯一底稿。短引用映射见字段字典。原生正文包若漏掉来源原子，宿主补成待核并接受该包。分析核验只发送 review。编制的目录调用见下节「编制实际模型调用」。部署状态见[交接](handoff.md)。

1. 分析的语义请求数为实际进入抽取的包数加准入的 review 请求数，OCR 另计。review 由按原文顺序预算分批的查漏请求、所需关系补审和显式作用域审核构成，见[核验怎么发](#核验怎么发)。分开统计计划条目、唯一逻辑请求和物理发送。每个逻辑请求最多初发一次、恢复三次，传输重试和合同纠正共用恢复额度。
2. 在 131072 上下文且输出预留 32768 的配置下，扣除 4096 安全余量，抽取和 review 的输入准入最多为 94208，含完整提示、框架、正文和支持证据。抽取保守按 UTF-8 字节估算，review 按实际 Token 估算。预留用于准入，供应商实际完成用量由回执统计。
3. 顶层合同被拒收时，按第 1 条的恢复额度尝试纠正。已采纳的包里如有引用对不上、范围盖不住或表格对不齐，宿主记待核并继续别的包或任务。人在确认或修订里处理待核项。
4. 修订只重跑材料摘要变了的任务，每个这样的任务最多 1 次写作和 1 次复核。未改任务不重发。
5. 模型不誊写宿主已知或能从冻结编号推出的原文、页码和表格。请求里的片段只供阅读，回包不得把该片段当作需要复述的答案。
6. 抽取包同时约束输入容量与预计输出工作量（BUG-261）。事项密度在抽取前只能估算，采用分包软目标和按范围的紧凑处置声明：
   - 分包软目标：对多范围抽取包，规划器将输入估算控制在 55,000 字节内，且单包需模型处置的正文范围数不超过 200（只排除宿主已审空白页与装饰图，保留空表行计数，因模型仍须逐行处置）；单条不可拆的大范围仍沿真实上下文预算（94,208）准入，不误判为硬阻断。抽取输出预留统一提升为 32,768。
   - 降低处置输出成本：`non_item` 用固定理由代码逐范围声明（见字段字典「抽取处置声明」），每个范围仍单独判断，不允许整组划掉，也不允许把一般合同条款或评标程序随手归入快捷码。

   这次改动的五问：
   1. 抽取软目标只作用于抽取。每个准入的抽取包发一次抽取请求，review 数由实际上下文扩展和预算决定，长节可能重复进入不同请求。全文件请求按第 1 条核算，候选复测估算见[改进路线](../../../plans/improvement-roadmap.md)。
   2. 多范围抽取包和不可拆范围按上面的软目标和真实上下文预算准入，输出按第 2 条预留。每包实际输出上界取决于供应商能力，候选复测记录实测完成用量。
   3. 分包变细增加上下文与固定提示的重复量；核验预算、失败和重试见运行回执。快捷码误判由独立原文清单和原始回包抽查。残余漏处置在确认页待核，业务人员核对原文后，实施人员用 [CLI `correct`](runbook.md#同来源业务纠错) 提交带证据的新增事项及该范围处置，再交独立核验。
   4. 同源事项纠正继承其基线修订的冻结来源和已提交抽取分包，保留包、证据选择器和原计划预算，只把计划根绑定到新领域修订。该路径发 0 次抽取，核验用新修订固定的预算，按整个修订生成 review 计划；实际重发量取决于完整请求回执的复用。当前分包回执的 `revision_budget_digest` 记录本修订准入预算，计划中的 `budget_digest` 保留原抽取预算。来源或作用域变更按各自流程重规划。已有修订的恢复继续要求其固定执行身份与预算一致。
   5. 不誊写：处置只回短引用 ID 和理由代码（`other` 或 `unresolved` 时给简短理由），宿主展开为持久化中文说明。

   同源纠错的跨包证据与宿主问题保留（BUG-269、270）：
   1. 仍沿用同源纠错的零抽取流程。核验计划跟随修订后的事项及证据重算。
   2. 事项可显式引用同一冻结文档版本的完整原文范围。每条事项仍至少有一条其原包正文引证。附加引证随该事项进入核验视图，计入完整请求预算。
   3. 宿主用冻结原文核对引用身份与逐字引文。保留可信旧回执中的未改包、仍未决范围的宿主问题和分级。原超预算导致未处置的正文仍待核时，保留其预算硬阻断。独立核验记录新增语义疑点，由原人工入口处置。
   4. 冻结来源、原抽取包及其查漏目标归属沿用基线。未改包保留原产物引用，复核按修订后的请求执行。
   5. 修订单仍只引用原文范围和必要引文，宿主装载原件。未改范围、宿主问题来源也由宿主读取基线回执。

7. 具体触发条件须进入事项（BUG-265）。多个独立条件共用后果时，可在同一事项中明确列全各条件，也可分成多条事项。每个条件保留适用范围及必要原文引证。事项正文或结构化触发字段须保留其事实含义。独立核验对照原件判断遗漏。该要求沿用现有抽取和核验次数，不新增调用阶段；多个条件仍计入单包实际输出，包和请求预算按第 2、6 条执行。无法判断的条件经核验进入待核，由业务人员按第 6 条出口补录。修订按完整请求身份确定重跑范围。模型只写事项的语义事实及必要引用，宿主可推导的编号和原表无需誊写。

8. v2 文本抽取使用严格 Schema（BUG-266）。同源生成 Schema 位于 `response_format.json_schema`，该格式记入执行规格。
   1. 全文件请求数按原分包和第 1 条的调用、恢复额度计算。
   2. Schema 只传一份，分包、初发和纠错均按实际完整请求准入。输入边界和输出预留按第 2、6 条执行。输出的累计实际用量按回执结算。
   3. 保留回包合同校验及原始回执。端点拒绝格式时按现有失败流程处理，由部署人员核对 Chat 路由。范围和语义问题仍按第 6 条由人工核对、补录后独立核验。
   4. 按完整请求计算摘要，严格格式和先前的 JSON 对象请求有不同身份。同源事项纠正沿用第 6 条的零抽取路径。
   5. 模型仍只输出事项、未被引证的逐范围处置、关系和问题。宿主从有效证据推导处置索引。

对照开源项目，不再在 `verify` 里面补拒收来假装收口：

- [Docling](https://github.com/docling-project/docling) 和 [Unstructured](https://github.com/Unstructured-IO/unstructured) 只冻一份带位置的文档。后面的任务只加标注，不另做一套原文字段。
- [Haystack](https://haystack.deepset.ai/overview/pipeline) 把建索引和生成分成两条管道。分析图在 `confirm` 结束；编制按[编制架构](authoring-architecture.md)读取固定的可用快照。
- LangGraph 的固定图是 `register → freeze → extract → verify → confirm`（`workflow/graph.py`）。`locate`、`associate`、`joint` 不是图上的节点，也不发给模型；`verify.md` 只描述 review（BUG-253）。跨页、跨节原文由宿主装进同一次 review。

## 编制目标设计：一条要求链（已决定，未实现）

2026-11-19 决定，实施步骤见[计划](../../../plans/single-requirement-chain.md)。下一节「编制实际模型调用」仍描述现状，新链上线后改写。

- 分析事项台账是编制唯一的要求来源。编制只决定放在哪、怎么写：先由格式章节和提交类事项生成分册、章节和原式表，再把事项短 ID 归属到响应位置，模型只回 ID。不再逐原子重新分类全部原文，也不再有读全文的请求。
- 覆盖分母是分析事项。分析漏报从分析的待核或修订出口处理，编制不兜底重抽。归属不到位置的事项进缺口清单。
- 保真范围：原式表格、固定文字、签章位置由宿主从冻结网格照原样复制；其余正文用解析文本加引用，解析瑕疵记为解析器缺陷。
- 第一份真实文件通过[最低验收线](acceptance.md#最低验收线)之前，不新增协议或阶段。

### 新链结构：格式章节选择

新链的分册、章节和原式位置由 `bid_format_source_outline_v1` 生成：模型只从投标文件格式章节选文件标题，宿主从标题复制原文到下一份文件之前，表格、空位、签章和表注照原样保留。不扫描格式章节以外的技术或服务标题，采购需求作为服务方案的写作依据。格式章节以外的必交格式由提交类事项补位，见下节。

提示要求单独成行的文件名标题（例如“承诺”）、带子编号的格式（例如“5-1”“8-1”）以及单独成节的每种可选提交方式各成一章，同一行用“或”连接的择一文件只成一章；正文里的承诺句和标题注明“不适用”的格式不是章节。五问：

1. 全文件固定 1 次逻辑请求，不随规模增长；宿主兜底路径为 0 次。
2. 单次输入为格式章节的短标题行和固定提示，安服约 9 千 Token；输出为章节标题引用和名称，随格式数线性增长，远低于输出预留。
3. 多选出的章节只是多一个空位置，归属不到事项时留空，编制人员可在 Word 里删除；漏选的格式由提交类事项补位或进入缺口清单。拒收按现有纠正额度处理。
4. 改提示会改变这 1 次请求的身份，已有大纲照常可用；重新生成大纲时重发 1 次。
5. 模型只回原文行引用和原文片段名称，不誊写模板正文。

### 新链：格式补位与事项归属

大纲执行选用 `single_requirement_chain_v1` 时走新链：格式章节选择（上节）→ 格式补位 → 编译 → 事项归属。不跑 M、B、C、P、F 和原文选择。默认入口仍是旧链，按[计划](../../../plans/single-requirement-chain.md)第 3 步验收后切换。

格式补位由宿主完成。提交类事项（`submission_requirement`）的 `submission.documents` 点名的文件在结构里没有同名章节、且事项引证不在格式章节内时，宿主在引证所在页及其前一页找与文件名完全一致的单独标题行，从该行复制到同一文件全部提交类事项的最后一条引证，补成候选原式章节，按原文位置排序，在位置目录里标为 `outside_format`。宿主分不出这份文件是随投标文件提交还是签合同时才签，由归属判断：没有任何事项落入的候选章节删除。找不到标题行时不补，这些事项照常参与归属。

事项归属沿用试点验证过的短 ID 协议，按预算把已核验台账分批，每批一个逻辑请求。输入是本批事项的语义字段和引证页、固定的响应位置目录（位置短 ID、标题路径、类型和原文开头）。每个事项恰好回一个结论：位置短 ID、不需响应的理由代码，或 null 表示待核。字段和理由代码见[字段字典](field-dictionary.md#新链事项归属)。宿主拒收整批的重复、遗漏、越域 ID 和未知代码，按现有纠正额度重发。落到位置的事项写入该位置的 `rule_refs`；`document_wide` 进 `constraint_rule_refs`；其余不需响应的理由记 `outline_rule_excluded` 并写明理由；待核和未采纳批次的事项在覆盖台账中为 `pending`。

五问：

1. 格式补位 0 次。事项归属为 ⌈事项数 / 每批事项数⌉ 次，每批最多 240 条且须通过预算准入，随台账规模线性增长（安服整份 715 条可一次准入，但模型只回了 3 行，故设软上限）；加上格式选择 1 次，大纲执行共 1 + 批数次，不再有读全文的请求。安服 715 条为 3 批。
2. 单次输入为本批事项语义和位置目录，按现有窗口准入；输出每个事项一对短值，上界随本批事项数线性增长，宿主按最长合法回包估算，须落在输出预留内。
3. 新问题是归错位置或判错“不需响应”。出口：覆盖台账和 Word 里逐条可见，编制人员改动或在待办里处理；分析漏报仍由分析修订处理。整批拒收在纠正额度用完后该批事项全部留待核，其余批次照常采用。
4. 台账或结构变化时重新计划批次；完整请求摘要相同的已采纳回包须重新校验后复用。只改一条事项时，只有它所在的批次重发。
5. 模型只回事项和位置的短 ID 或理由代码，不回抄原文、不填值、不签署。

## 编制实际模型调用

本节按当前源码记录编制的实际请求次数（BUG-251），代码变了就同步改这里。缺陷条目里的旧公式（如 `2A+M+B(L)+C+ΣP+ΣF`、`3+B+C`）只描述当时的局部改动，以本节为准。下面的计数都是逻辑请求次数。每个逻辑请求另有现有的恢复额度（首次加三次），成功回执复用不重发。

Web 端一份标书分两次执行：先跑大纲执行（`web-outline-*`，`outline_only`），再跑正文执行（`web-document-*`，固定使用已生成的大纲）。用户保存 Word 后可以另外请求复核。

已保存版 [PDF 出件](../../bidding/onlyoffice.md#pdf-与报告) 每次请求转换一份整稿，转换次数只随用户导出的版本和重试次数增长，模型调用新增为零。输入 DOCX 和输出 PDF 分别受现有文件限额约束，最大各 50 MiB，配置更低时按配置。版本冲突由用户刷新并重新选择，服务或容量错误可从同一版本行重试。修订后只在用户需要导出该保存版本时执行一次转换，由宿主传输文件字节。

### 大纲执行（有可读冻结来源时走目录编译）

| 阶段 | 任务 / Prompt | 次数 | 随什么增长 | 单次输入 | 代码入口 |
| --- | --- | --- | --- | --- | --- |
| A 目录规划 | `directory_plan` / `directory_ref_plan` + `_v2` | 固定 2（两个独立槽位）；`bid_format_source_outline_v1` 时为 1 | 不增长 | 装入整份来源，随文件变大 | `_request_directory_plans` |
| M 章内材料 | `directory_material` + 来源分组、闭合、响应表单附加段 | 1 | 不增长 | 装入整份来源，随文件变大（BUG-211 在 118 页时超限） | `_request_directory_details` |
| B 要求归属 | `directory_requirement`，原生合同时追加 `directory_requirement_native` | 原生合同：按预算分包，每包 1 次；旧路径：约每 600 行整页为一块，每块 1 次。并发 2 | 随来源原子或行数线性增长 | 按包受预算约束 | `_request_native_requirements` / `requirements()` |
| C 归属分类 | `directory_classification`，原生合同时追加 `_native`，有已核事实时追加 `_reviewed_facts` | 装得下就 1 次完整 C；装不下改为文件级 G≤1 次，加上作用域包 S 次（S 不超过不可拆单元数） | 完整 C 的输入随全文和待核案例增长；S 随案例数增长 | 完整 C 可能远超预算（BUG-244 中为 490,874），超限时整组留待核 | `_request_joint_classification` |
| P 长章展开 | `directory_parameter` | 每个非空行数不少于 25 的叙述章 1 次 | 随长叙述章数增长 | 单章 | `_request_directory_details` |
| F 响应原式 | `directory_response_form` + `_v2`/`_v3` | M 选中的每个逐条响应原式 1 次 | 随选中的原式数增长 | 单个原式的完整来源范围 | `_request_directory_details` |
| 原文选择 | 任务 `directory_parameter`，Prompt `directory_native_body` | 按原文选择规划分包，每包 1 次 | 随大纲目标的原文量增长 | 按包受预算约束，含纠正余量 | `resolve_native_bodies` |

- B 和 C 有两套合同，由环境变量 `KNOWLEDGEBRAIN_TENDER_NATIVE_REQUIREMENT_CONTRACT` 决定，后继执行沿用前任已经固定的合同。设置了原生要求合同时不跑原文选择；未设置时，新的大纲执行会启用原文选择合同（`document_execution.py`）。
- 原生合同下，B 对全部原文原子逐一给出去向，C 再做全文件分类。这相当于在编制里又抽取了一遍要求，和分析台账是什么关系仍待定（另立问题）。
- 冻结来源不可读或缺失、自动大纲没有可用响应位置时，保留诊断并报告可恢复失败。重新登记或冻结原件后可生成新候选，也可继续使用已有大纲。这个分支不发模型、不改变请求容量，重新生成使用新来源快照，诊断由宿主记录。

#### F 原式的条款号

原式依据支持逐条展开、重复区紧接「条款号」表头，且该列在重复区内全空时，`sequence_column` 绑定这列。每行首个正文引用须从冻结原文的行或原格内行首选入完整的点分数字条款号。宿主从这个引用复制条款号，从所选片段复制原文，保留固定格、未使用空行和签章、表注。已有连续整数的原式沿用原序号和续号。仅要求据实列出偏离、资料或报价的原式仍按其职责保持原样。

- 全文件仍是每个 M 选中的响应原式一个 F 逻辑请求，随表数增长。单次带完整所选来源页、原表和填写依据，最坏输入受当次模型输入预算约束，合法输出上界由来源原子数、短引用与填写依据索引估算，须落在输出预留内。使用 131,072 上下文且启用分词时，两项上限分别为 94,208 和 32,768 Token。
- 条款号缺失、引用截断或布局无法核定时，保留原表及已选来源，由编制人员按原件核定后手工列条款或修订重试。只修改一张表的选行或来源范围时，受影响的 F 逻辑请求至多一个。改 F 提示词会改变新执行的 F 请求摘要；恢复在途执行须使用匹配原规格的版本。
- 模型只选现有短引用和列位置。条款号、正文、固定模板和已有空格由宿主复制，企业应答、偏离情况、说明和证明位置留给企业事实或人工核定。

小结：常见情况下，大纲执行有 `2A + M + C` 这 4 次固定发送，其余 B、S、P、F 和原文选择按规模增长。A、M 和完整 C 的单次输入随整份文件增长，所以「单次输入不超过 94208」现在是靠超限拒收和留待核来保证的，并不是靠分包本身保证。这是已知缺口。

### 正文执行（固定大纲）

| 阶段 | 任务 | 次数 |
| --- | --- | --- |
| Q 知识检索 | HTTP，不是模型调用 | 每条检索词 1 次 `search`；每份命中文档另加 1 次 `document` 读取原件身份；需要原件时每份再加 1 次 `file`。每次操作沿用首次加三次的恢复额度 |
| 依据 | `authoring_basis` | 按预算分批，每批 1 次 |
| 结构复核 | `authoring_structure` | 每次正文执行都跑（生产不传 `directory_plans`），1 次请求，输入是整棵大纲 |
| W 写作 | `authoring_write` | 每个有允许依据的任务 1 次；任务装不下时拆成多个部分，每部分 1 次。全人工或全无依据的位置不写 |
| 正文复核 | `authoring_review` | 按预算分批，每批 1 次 |
| 改稿 | `authoring_write` | 每个有可改稿发现的任务至多 1 次 |
| 再核 | `authoring_review` | 受改稿影响的任务按批再核 1 轮 |

每个任务最多 2 次写作（初稿 1 次加改稿 1 次），所在批次最多复核 2 轮。依据、复核和再核都是批量请求，次数取决于预算分批，不等于任务数。

用户保存 Word 后请求复核（`review_saved_word`）时，按预算分批发 `authoring_review`，每批 1 次（`saved_word_review.py`）。

本节用阶段名称加任务名区分请求。字母 R 在旧条目里既指原文选择（BUG-221、250），也指正文复核（下文「不计 W/R」），阅读旧条目时要按上下文区分。

## 统一事项与来源关系

事项只共享必要身份、类型、内容及原文证据；具体字段、可选细节及模型交换示例统一见
[字段字典](field-dictionary.md)。义务、评分规则、后果规则、文件及提交要求保留各自含义；
领域标签仅用于导航和查漏，不能据此排除其他类别的要求。

- 可选字段有原文依据才出现，不填占位；合法零分、零数量必须保留。
- 省略不证明原文没有、不适用或核验通过。含歧义、缺必要上下文或待解析引用时登记问题。
- 一段可产生多个原子事项并共享证据；拆分必须保留共同条件、分档、公式、封顶和作用范围。
- 关联记录评分针对什么、后果由什么触发、义务需要哪些原文明示的文件，以及补遗修改什么。
  只引用真实存在的事项并保留来源证据；未知目标先记未决，不从章节标题编造事项 ID。
- 部分补遗通过有证据的决议明确修改范围、全部保留内容及替代事项，纯删除不要求虚构替代。
  当前视图投影独立核验接受的决议，保留原项历史；不按发布日期自动覆盖，不靠宿主做范围相减。
- 适用性只分析原文的标段、主体、条件和例外，不判断企业是否符合，不记录评分采纳或准备完成状态。

例如“负责人须持 A 证；持 B 证加 2 分；未附 A 证复印件则否决”，应表达资格义务、
评分规则、文件要求及否决触发关系。不能把 B 证加分当作强制资格，也不能把否决扩大到所有人员材料。

## 核验怎么发

1. extract 只携带本包正文、必要上下文及其章节信息，不发送全局目录。不在本包出现的内容不等于全文缺失。
2. 抽取完成后，verify 只发 review。宿主对整份来源的待核正文及同页、同节范围取并集，按文档和原文顺序预算分批。每个需要查漏的正文范围只在一个主请求中列为 `dispositions` 目标。每个请求仍装入适用条件、事项引证和关系所需原文；这些原文可以在请求之间作为阅读上下文重复。未在同一主请求覆盖的关系另行按预算补审，显式人工作用域单独核对，二者均沿用 review 且只检查其关联和解释。核验覆盖须有查漏目标所属请求的有效回执。模型只回判断和问题。
3. 缺页、残页由宿主记 `analysis_page_source_unavailable`。漏报的来源原子补成待核。这两类都不再发下一轮模型。
4. 抽取已经写下的关系随 review 一起看。模型没有写进台账的跨源组合不再另开发现轮，留给人处理。重复引用、未知编号、上下文环、正文与上下文重叠仍然拒收。
5. 目标找不到、正文不可读、含义不清时保留问题，转人工。不递归补读，不访问外部链接。漏抽或错项走显式修订，不能由核验静默改写事项。

正则或关键词不能当作最终业务判断。晚发布的补遗不自动覆盖全文，必须有明确的修改对象、范围和来源依据。

review 按完整请求的真实上下文预算准入。使用已校准的 Token 计数时，正常分批目标为 32,768 输入 Token，单个不可再拆的完整范围或依赖组仍按实际上下文准入。输出按「当前发送边界」的配置预留。超预算工作单元记待核并继续别的请求，原件、事项与关系证据保持可追溯。来源或领域修订重新生成核验计划，完整请求身份相同的回执可复用。

PDF 逐字行在本页表框内、与唯一表格单元格的完整原文行匹配，且该单元格有勾选选项时，核验将匹配的完整表格行带入该目标的阅读上下文。相同表格行已可见时复用已有视图。重复匹配需要按原证据判断适用性。

同一冻结 PDF 的完整表格范围与逐字行分属不同范围时，查漏请求补入已引用对方范围的事项及其完整引证。匹配要求在同页表框内，逐字行唯一对应一个单元格的完整行，或同一表格行中两个相邻单元格的完整首行。匹配允许版式空格差异，保留 ASCII 字母和数字之间已有的分隔，原文和引证仍按冻结内容发送。片段、重复、越框和无法逐字核对的范围继续按原证据核验，歧义留待人工。补入事项不改变原处置及其查漏归属；同一表格行内尚未抽出的义务仍须核验。

1. 同一目标仍只属于一个查漏请求。正文目标按预算分批，随目标数和已绑定引证增加。补入表格行或既有事项可能改变分批数，核验次数按准入的主请求和既有补审请求计算，恢复额度沿用「当前发送边界」。
2. 完整表格行、补入事项和引证计入实际输入，分批目标、硬准入和输出预留沿用上文。
3. 匹配只决定提供哪段原文。适用性由核验读原件判断，语义待核由人工处理。若单个范围与其完整上下文超过硬预算，宿主记预算待核。
4. 同一修订恢复时沿用已经保存的请求准备和计划。新来源或新领域修订按当前规则重新分批，按实际完整摘要决定复用和重发。
5. 核验仍只回判断和问题。宿主记录查漏覆盖。

跨章适用性沿用已有作用域审议。业务人员在已登记的同一冻结原件中定位适用条件及目标，例如前附表和通用条款，由实施人员提交 `review-scope`。宿主只对受影响原件和显式目标装入控制条款及绑定，完整审议结论与全部引证随该决定的作用域补审。查漏或关系补审请求读到某决定的控制条款或目标时，同一请求也附带该决定，避免模型对人工已审的作用域重复报疑点（BUG-299）；没读到的请求不附带，请求身份不变。跨文档补遗仍按已有补遗与冲突规则处理。定位不唯一、缺件、含义不清或超预算时留下具体问题，分别按人工审议、来源补齐或宿主预算出口处理。

1. 全文件沿用现有抽取和核验计数；作用域补审每份显式决定最多增加一个逻辑 review，不为其他原件增加作用域请求。附带决定不增加请求数。
2. 每次请求的完整条件、相关原文和作用域信息都计入现有输入准入及输出预留，整组超上限留作预算问题。附带的决定计入所在请求的输入，最坏为该请求读到的全部决定。
3. 按[状态与修订](#状态修订与恢复)处置，操作见[运行手册](runbook.md#提交与确认当前-v2)。模型仍可对附带决定提出新疑点，由人工按原出口处理。
4. 作用域修订重建计划；只重发完整请求身份不同且获准的请求，同源事项纠错继续沿用已有零抽取入口。新增或修改一份决定时，只有读到其控制条款或目标的请求身份改变并重发。
5. 宿主装载冻结原件和审议引用；模型仍只回核验判断及问题。

## 状态、修订与恢复

运行状态的枚举及含义以[字段字典](field-dictionary.md)为准。必要来源缺失、作用域未审议、
覆盖或预算等分析不完整的硬阻断使用 blocked；执行/协议失败使用 failed；核验完成且无硬阻断即进入
waiting-confirmation，剩余语义疑点由人工在确认时逐条驳回或保留，分级见
[问题分级与人工处理](field-dictionary.md#问题分级与人工处理)。
当前版本确认有效后进入 analysis-ready，不再执行响应规划。

业务人员按原件核实外部引用是否是必要来源。已核实的必要附件由实施人员在 `revise` 的来源清单声明；缺件留在登记问题，补齐后按原来源身份重新提交。仅在当前请求不可见的引用先列待核。登记核实与缺件判断不新增模型调用或回包字段；核验使用既有预算，来源修订重新规划来源及抽取、核验，仍用完整请求身份决定实际发送。操作见[运行手册](runbook.md#提交与确认当前-v2)。

运行状态、模型请求状态、子操作回执和业务适用性分别表达；不增加按业务领域的状态机。
模型请求 succeeded 或子操作有回执，只证明响应保存或产物提交，不证明业务核验通过。
当前工作区已按上述边界区分协议失败和业务未决；完整验证及部署状态以交接为准。

来源变化使用 source_version；同来源业务纠错使用 domain_revision，重新核验并使旧确认失效。
业务格式使用独立 schema_version，旧回包不自动满足新合同。问题决议绑定具体问题身份、
来源/领域版本、证据及处理结果，不能按 code 批量清除。

成功回执和请求审计保留；所有调用失败包括uncertain都是首次加三次，可能重复计费，
详见[恢复合同](field-dictionary.md#失败执行的显式恢复)。仍在途的sent禁止并发发送，
新协议、重分包或改提示不能重置已有运行的重试额度。
旧运行记录保持原义，不改写成已经完成的新分析。每次部署与真实运行只记在交接，
文档目标不代表对应协议已经部署或通过实测。

## 交付、实施与验收

最终交付为来源清单、完整事项台账、评分与后果规则视图、关联及问题/决议记录。
各视图投影同一台账，不复制维护另一份评分或风险事实；存在阻断时也保留可读取的局部结果，
但不能宣称完整分析。analysis-ready 不证明投标人合格、实际得分或投标文件已编制完成。

1. **文档先行**：统一本文、字段合同、状态、交接及验收入口，清楚区分目标与现行代码。
2. **合同与纵切**：工作区已同步实现共享schema、提示、抽取/核验、摘要/确认和结果视图，
   贯通五节点，不接入旧 Plan；不只改终态名称或增加几个字段。
3. **语义与恢复回归**：验证正反语义用例、一轮补读、跨文档关联、修订确认失效、成功复用和 uncertain 有界重试。
4. **真实文件验收**：保留既有来源/作用域问题，完成必要裁决后执行五节点；分别报告合同测试、
   真实模型流程完成情况和人工标注的漏检/误报，固定模型通过不等于模型业务能力通过。

首批验收包含：同句资格/评分/否决/证明关系；无评分不补造；分档/公式/上限及合法零分；
扣分、不得分与否决区别；条件、例外、表头单位继承；部分补遗修改；跨包引用补读成功或未决；
必要附件缺失阻断、缺企业响应资料不阻断；修订后旧确认无效。它们是回归场景，不是全部业务清单。

## 与后续投标编制的衔接（设计边界）

最终业务目标是根据招标要求编制投标文件，包含大纲、规定模板、匹配的知识内容及有依据的
响应。本节说明后续设计方向；一期仍以分析确认结束，字段定义仍由字段字典统一维护。

以下编制流程按[knowledge_required_v2合同](field-dictionary.md#编制最小修订knowledge_required_v2)
统一；源码、部署和真实验证状态见交接，不以文档修订声明已验收，不增加主节点或复杂状态。

编制以“持续形成可编辑投标文件”为目标：资料缺失、未确认、响应不足或复核问题均不
作为生成、保存或导出的业务门禁，原文明示必填信息也可先留空/待补。文件生成与内容
是否满足要求分别报告；原分析确认仍保留其含义，不伪造完成。编制固定可用资料快照，分析确认和资料齐备不作为编制入口；具体执行与真实验收状态见交接。

技术方案按适用标段收集当前可用的技术参数及标准、实施与验收、服务与人员、评分及证明、
实质性约束和格式规则，保留已知条件、例外及补遗。尚缺内容标注待补，不作为生成前提；
要求完整性作为后续质量核对目标。项目现状、现有系统、业务
规模等必要背景可以是说明性原文，不必强行抽成事项；后续按冻结来源引用装载。
不能只以技术章节或domains标签筛选方案输入，事项摘要也不能替代必要原文及表格。

### 已确定的业务流程

上传招标文件是业务起点；企业资料、知识库和产品信息可随时提供，不要求
全部齐备后启动。下表是业务顺序，不新增六个分析节点或六次人工审批。
最终报价、单价、总价、折扣等保留字段，最后由人工填写；招标预算、最高限价和评分
数字照常保留。已有历史价格不自动采用为本次投标价格，不影响其他正文继续生成。

| 步骤 | 做什么 | 可见产物及衔接 |
| --- | --- | --- |
| 1 理解招标 | 读取可用原文与分析结果，整理背景、要求、评分、文件格式和提交约束 | 可追溯要求及具体疑点；资料不全或未确认不阻止进入编制，后续可继续补充 |
| 2 搭建文件结构 | 按本项目规定确定分册、目录、表格和附件位置；已有大纲调用同时选择support_origins并产生search_intents | 缺资料仍保留完整结构；宿主绑定引用并联合来源/意图，混合表单不因依据类型复制，不要求先选产品 |
| 3 准备候选资料与共同依据 | 宿主执行由实际原文/规则规划的有限业务检索词，不发送要求JSON作AND查询；仅汇总有知识支撑的共同安排 | supports共享实际原文和知识，保留范围、产品/版本及可读证明依据；无企业知识仍可写来源支持的背景 |
| 4 分任务匹配并编写 | 单次write匹配改写，每个block/fill选择target_ids及support_ids，附件选attachment_ids；宿主管正式引用和原表 | 企业应答未匹配留空；背景/源文可确定填值可选tender支持，不能把要求写成我方承诺；未知价格始终空白 |
| 5 汇总与复核 | 检查实际应答、附件及有候选却完整判空的语义结果，b/f/a精确定位删除；有足够支持的正文或语义空稿可一次定向修订 | 初审仅接口失败保留U0待核；初审否定先形成S0，改稿失败/空回包/再核不可用退S0；保留各稿及缺口继续导出 |
| 6 交付文件 | 按规定分册组装可编辑文件，保留空位并提供对应缺口清单 | 可继续编辑的投标文件及剩余事项；生成成功不代表资料已齐、已满足全部要求或已完成外部提交 |

步骤2/3可交错；有本位置允许支持的任务进入4，完成一批可复核一批。support_origins
只决定允许的依据及调度，不证明语义正确；模型仍须判断背景、企业应答及支持关系。
全人工/全无允许支持空位不写作、不正文复核；写作传输失败纯空稿耗尽恢复后记录运行
原因。有候选但模型完整判断不匹配的空稿仍独立复核，不能按“无正文”跳过漏匹配检查。
步骤5是内容改进，不是放行审批；步骤6可组装已有成果，不要求先关闭全部问题。补充
资料或修改方案后，只更新相关位置及必要的一致性复核，不固定重跑整份分析/标书。
大文件的调用按完整业务单元及输入/输出容量组织，不能按总页数要求模型一次写完。
最小验收包括“缺信息仍能获得可编辑文件”和“缺口不被编造成已满足”，详细内容质量
另外核对，不把未填内容误判为整个生成失败。

### 补资料与重新生成

1. 一次资料补充或更新动作作为一批，汇总受影响任务后更新；不随每个新增片段或检索
   结果反复重写。已开始任务使用固定快照，新资料用于后续更新，不增加确认或审批步骤。
2. 同一业务事实在多个位置使用时，补充一次即可更新相关内容；按已有引用及适用范围
   关联，不能只因字段同名就跨标段合并。实际文件中需要重复出现的响应位置仍然保留。
3. 重新生成另存新稿，保留原稿和已有修改，说明本次更新范围。首版不做Word人工修改
   自动合并，也不承诺识别尚未读取的外部编辑；无需增加编辑器或通用版本管理平台。

以上属于原步骤的操作规则，不增加业务阶段或固定模型调用。更新批次按受影响任务
去重后处理，保持原输入/输出预算；共享事实联动及新稿保存由宿主管理，模型不回抄名单。

全过程须可追踪“来源事项／评分点 → 响应位置 → 采用的内容与证据 → 生成结果”。有章节
标题不代表已回答要求，检索命中不代表企业满足条件，文字齐全不代表实际得分。
语义匹配、响应充分性和证据适用性由模型及必要的人工判断；宿主管理身份、引用、版本、
来源装载、覆盖及执行。企业资料不足不改变招标要求，不用生成文字冒充证书、业绩或测试结果；
缺口随受影响内容展示，其他独立章节可以继续起草。

招标规定模板中的固定文字、表格结构、字段及签章位置须保留来源；企业写作模板用于组织
内容和样式，不覆盖招标规定。先在Python中完成分析到编制的闭环，复用分析台账，通过
引用读取必要原文，避免固定再做一轮全量要求抽取（现状未做到：原生合同下大纲的 B、C 会重新分类全部原文，见 BUG-254）；编制消费当前可用资料的固定快照
独立启动，原有确认结果可作为依据但不作为入口开关，不在confirm后增加必经第六节点。

业务上，一项要求可能同时涉及方案、偏离表和证明附件，先用真实样例明确必要的响应位置
及引用，不先新增通用映射框架。

技术响应以功能如何满足及实现方案为核心；品牌、型号、版本和配置为可选补充，不作为
写作前置，也不新增选型确认门禁。能匹配则采用，缺省时继续编写有依据的功能方案；
原文明示某处必须填报时仅保留该处待补，不编造事实、不暂停其他内容。规定骨架、知识
匹配与有允许支持的独立写作任务可并行。v2合同统一supports/support_ids，
宿主适配为持久material_ids及新增source_refs，不迁移全部旧稿。source_id仍指原表，
同表不同格可取不同来源；不以proposed或approach兜底生成企业方案。真实附件须有
可判断证据，未读原件不能仅凭标题选入，content_ids中的a1只移除该附件。
U1按自身内容重新分配b/f/a别名，U0旧序号仅用于历史定位，不直接删除U1。
正文复核用reject_content明确判断当前文字是否失真，宿主按实际短引用执行剔除；
不从自由问题code猜采用动作，纯遗漏/待补/技术复核失败不删除正确内容。父级导航
优先使用已确定章节关系，不额外重述子表要求；真实规定的摘要表和原要求仍保留。
四项语义职责、skill边界、共同依据及
完整交付验收见[编制架构草案](authoring-architecture.md)，正式结构见字段字典，实际验证状态见交接。

### 调用、预算与修订约束

1. 分析的模型发送是每个放不下的冻结包 1 次 review，见上文「当前发送边界」。编制的实际阶段和次数见「编制实际模型调用」，不再使用 `L=S+A0+F0+…`。失败重发、合同纠正和业务改稿另计；成功回执复用不增加发送。每个请求连接失败仍是首次加三次。
   大纲O含support_origins/search_intents，语义匹配包含在W，不增规划或匹配轮；
   全无允许支持和人工位置不计W/R，有招标来源支持的说明可写，有候选的语义空稿仍计R。
   知识查询Q次按首次加三次最多4Q次HTTP尝试，无命中/不适用不重试至命中。后续批次及纠正上限须在
   纵切设计中确定，未知项不记零，不承诺全流程线性增长或提前给出费用上界。
2. 单请求按完整提示、相关要求与规则、必要来源和表格、采用资料及实际输出工作量准入；
   引用让宿主按需装载，不能代替模型需要理解的内容。按章节任务预算输出，不能只核算输入，
   也不能未经实测沿用分析输出预留；输出包括大纲检索意图及逐block/fill目标和support引用，
   supports中必要原文/知识仅发送一份。检索词最长256字符不等于限制原要求，完整不可分任务
   超限时记录待调整任务，不静默删约束。
3. 来源不清或事项错误沿分析修订出口处理；资料缺失由用户补充或选择有据替代；模型保留
   匹配歧义及响应不足。本次先留空/待补并继续生成和导出，不等待修订或补齐；补充后
   复核相关内容。明确无依据才移除，初审接口不可用保留尚未否定的U0待核；初审否定后
   形成S0安全稿，修订失败或再核不可用退S0，不让已否定内容复活。各稿及回执保留，
   不把未核对写成缺资料，不增加业务状态机或循环重读。
4. 同一分析修订下的样式修改不触发重新抽取；来源或领域修订按现行合同重验并使旧确认
   失效。后续根据实际引用依赖及完整请求摘要确定重跑范围，公共选型或承诺变化须复核所有
   受影响章节，不能预先承诺只重跑一个章节或静默沿用旧稿。grounding_policy进入
   basis/write/review真实请求及执行spec，新策略不能静默采用旧策略无依据正文。
   v2改变已有outline输出，旧106页样例的17份来源回包不能直接复用成新意图结果，
   须重新预审O及费用。后续明确重审用新执行继承前驱，真实理由进入请求；同ID完成稿
   不覆盖，不清缓存或加盐。单query回执仅在范围/知识版本可证明一致时复用，目标重新绑定。
5. 模型只判断语义关系、选择相关内容及生成回答；宿主持久绑定引用并派生任务覆盖和反向
   索引，不要求模型重新誊写已知来源元数据、完整章节名单或覆盖清单。

### 最小纵切验证

先选同一真实文件中的“技术条款＋方案评分规则＋技术偏离表”，追踪其分析结果如何进入
大纲、表格、知识证据和最终正文，同时保留必要背景、缺材料及响应冲突的处理结果。
分别核对要求有无遗漏、方案是否具体回应、评分依据是否展开、表格和证据能否回溯；
不能仅以结构通过验收。真实材料及调用证据保存在仓库外的私有证据目录，仓库只保留合成示例。
用这条业务链确定最小对接字段及是否需要跨章目标扩展，再实施后续协议。
