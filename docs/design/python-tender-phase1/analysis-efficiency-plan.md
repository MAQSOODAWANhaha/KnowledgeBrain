# 分析效率修复方案

源码已落实本方案，对应BUG-026及其新样本证据BUG-080；
字段以[字典的统一合同](field-dictionary.md#关联与联合核验的专用合批合同)为准，
实际运行和验证进度只记录在[交接](handoff.md)。

## 目标与取舍

保留分析五节点、全源独立核验和全部候选，解决“一个语义依赖组必占一次模型请求”的
固定开销。只修改associate/joint的请求组织、结果归属和恢复；沿用现有CAS、模型回执、
工作单元与调度，不建设通用Agent平台，不引入DeerFlow运行时。

必要的重复读取包括抽取后的独立全源核验、跨来源共同理解、提案后的独立反查。
同一阶段不同目标共用的原文可以同批发送一次，但不能删除目标，也不能由相似文字或
共享引用推断两个业务问题相同。引用可用于宿主装载完整资料，不能假设模型能凭CAS引用
读取未发送的内容；原文摘要不替代条件、例外、补遗和表格结构。

## 借鉴DeerFlow的范围

仅参考当前源码中适合本业务的设计，不迁移框架：

| 参考设计 | 本项目采用方式 |
| --- | --- |
| [最少且有净收益的委派](https://github.com/bytedance/deer-flow/blob/main/backend/packages/harness/deerflow/agents/lead_agent/prompt.py) | 保留固定子操作，不按每个事项或候选创建Agent；比较完整下游成本后再扩大并行 |
| [独立任务上下文](https://github.com/bytedance/deer-flow/blob/main/backend/packages/harness/deerflow/subagents/context_snapshot.py) | 每次只发实际任务、完整依据和必要纠正意见，不携带整段运行历史 |
| [产物外置及回读](https://github.com/bytedance/deer-flow/blob/main/backend/packages/harness/deerflow/agents/middlewares/tool_output_budget_middleware.py) | 复用现有CAS；模型内共享池去重，模型外保留完整原件及定位；不采用首尾截断丢弃证据 |
| [执行、验收及局部恢复分开](https://github.com/bytedance/deer-flow/blob/main/backend/packages/harness/deerflow/subagents/batch_service.py) | 完整传输回执与逐组语义结论分开保存，成功组复用，失败组消耗原剩余额度 |

Skills适合封装已有合同及操作说明，按操作加载；目前不新增Skill发现系统或另一套事实库。
DeerFlow的batch逐item运行SubagentExecutor，并没有自动将共同证据合成一次模型调用。
因此本方案的效率收益来自下述业务请求组织，不能归因于换框架或增加Agent。

## 最小实现

1. 保留现有共同issue及续报依赖形成的逻辑组。每组候选和完整来源闭包不拆。
2. 按来源身份重叠做一次确定性排列，再按实际输入和输出预留顺序装批。排序只影响
   物理请求，不推断语义；请求内文档和原文仍按冻结顺序。并集仅合并同身份、同内容的
   副本，不跨文档或不同区间按相同文本去重。同身份内容不一致时不覆盖或强行共批，
   保留原组请求处理。
3. 一批共享完整source_views/items/relations等对象，各work_unit独立指定目标并返回
   结果。normalization_version=11先登记完整共享来源，再登记成员和基础池，新增提案
   不改变同一依据的短号；说明文字使用实际引文或名称，不依赖短号代表语义。组内继续
   使用现有整体接受规则，首版不增加组内逐decision部分接受。
4. 先处理共同反证的明确归属，再保存各组结果。某组finding只影响该组；模型发现跨组
   反证时显式列出受影响work_unit_ids，宿主不按共享来源猜影响范围。保留原批全部成员，
   以target_work_unit_ids指定本次待回答子集；共同反证也能指向此次未待回答的已成功
   兄弟组。阶段最终汇总按这些显式反证保留未决并排除受影响决议的接受，成功传输回执
   不改写，不为新意见自动开启递归修复。完整JSON收到前不接受截断流中的部分组。
   当前接收合同normalization_version=12只在成员适配视图中省略精确的空
   `shared_findings=[]`；非空或错误类型保留原回包并反馈移到明确归属的外层，宿主不
   猜归属。发送载荷、Prompt、共同意见/兄弟结果及每组首次加三次额度不变，旧11执行
   不热替换；可离线重放既有完整回包验证此接收修复，不为同一传输重新付费。
5. joint保持独立调用，优先沿原合批边界核验有决议的目标。保留associate实际可见的
   完整共享依据、全部必要提案及反证，不从最终quote反推依赖并裁剪来源。无决议组仍
   按现有规则保留未验证关系及finding，不为了关闭它们额外创造核验任务。
6. joint实际请求超限时只减少目标组，保留完整共享依据重新准入；单组仍不可容纳则走
   原容量/来源修订出口并保留未决。该情况必须计入效率验收，不能靠丢依据获得“提速”。

仅保留已有的“传输请求、逻辑组、组结果”三个边界，不新增数据库任务表、RunStatus或
主节点。单批来源失效时，受影响结果需重验；保持完整共享依据意味着局部修订可能影响
同批兄弟组，这是合批的实际代价。

## 容量选择与证据

同一冻结台账的离线重建保留192个逻辑组、195候选，逐组原内容可无损恢复。以下为
暂定合批载荷的输入估算，不是计费Token、真实模型结果或正式字段落地后的固定请求数：

| 方案 | associate请求 | 估算输入 | 相对原输入 |
| --- | ---: | ---: | ---: |
| 当前逐组请求 | 192 | 2,567,798 | 基线 |
| 原顺序装批 | 60 | 1,817,339 | -29.23% |
| 一次来源重叠排列后顺序装批 | 55 | 1,317,863 | -48.68% |
| 每步重新搜索最优重叠候选 | 54 | 1,313,782 | -48.84% |

选择第三项作为真实对照候选；更复杂搜索只再少1请求、4,081输入，不采用。一次重叠
排列需O(G²)宿主集合比较，装批顺序扫描，不新增LLM调用；不把它描述为线性排序。

试验最多4个逻辑组，`output_reserve=max(32768,24576*k)`，k为本次回答的组数，
context=131072、safety=4096。最多4组是可校准的容量参数，不是按文档业务编号硬编码。
对应1/2/3/4组的输入准入上限为94208/77824/53248/28672；实际测量还包含提示及反馈。
正式字段、Prompt或模型变化后重新测量，不复用本表作为发送许可，不新增多套环境变量。

24k/组依据当前完整单组回执P95约18k加余量提出。它不是输出上界；模型还会消耗推理
Token，当前样本约93%的associate completion属于供应商报告的reasoning。只缩JSON或
增加并发不能推导耗时降幅。现请求没有wire输出硬限，最坏输出长度无法由数组数量严格
限定；超出供应商容量或截断按既有失败恢复处理。不能把预留值写成max_tokens的事实。

## 重试与修订

- 逻辑目标身份用于累计尝试；组结果的复用摘要包含实际完整共享依据、任务、协议、
  Prompt和模型；物理request_digest继续绑定精确请求。批号/整份plan_ref仅用于导航，
  不因无关批次调整使全部成功组失效，也不因换批号重置失败额度。
- 所有执行失败沿用首次加最多3次。整批传输/JSON失败对全部参与组计一次；完整回包
  中局部缺组或坏组只纠正该组，原成功组保留。拆目标重试仍使用原共享依据和剩余额度。
  有效的“无法解决/不接受”语义结论保留未决，不无变化重试到模型同意。
- 共享finding的归属无效时不能先接受可能受影响的兄弟组；保留完整原回包，带明确
  错误在原额度内纠正，耗尽后进入既有未决/恢复出口。不能默默忽略反证。
- 发送前在原租约事务内核对所有成员尝试及在途sent；组结果落库中途崩溃后先重放已
  成功物理回包、补齐组结果，再考虑新请求。保留succeeded/uncertain含义，不清缓存、
  不加盐、不宣称远端exactly-once。发送前失败也须在原持久额度内累计。
- 本次升级使用新冻结执行，不热换正在运行的协议。修改共享verify提示时全部verify
  摘要变化，不能声称仅重跑associate；新全流程执行需另计OCR/抽取等实际重跑费用。
- 同一协议内恢复成功精确请求不重新付费；纠正目标d组时只重试d组及必要后续核验。
  内容修订须重新规划依赖：实际共享依据改变的组及下游重新运行，不保证只影响一组，
  最坏仍可能覆盖完整分析。协议升级不引入跨版本缓存适配层。

## 修改前五问与验收

1. **全文件调用与增长**：令O为OCR、E为抽取、R为全源review、L为全部locate
   （discovery加reference）、G为关联逻辑组、H为需joint的组（H≤G），A/J为装批后的
   实际请求数。无失败的分析调用为`N=O+E+R+L+A+J`，不是简单把192换成55便结束。
   在每组最多4次、重试不产生新语义组的条件下，含拆批的保守发送上界为
   `4*(O+E+R+L+G+H)`；不能用`4*N`约束可能拆开的重试。该上界限于同一自动执行额度，
   不含用户另行恢复的新命令、内容修订或新运行费用。下游未规划时报告未知。
   候选发现若需m个容量块全配对，块组合仍可达m(m-1)/2，候选数量也可平方增长；
   本次减少重复传输常数，不声称任意规模都线性或消灭所有耗时。
2. **单请求最坏输入输出**：按上节的完整请求准入及输出预留；joint另按实际新增
   决议/反证重新测量。输出无严格上界这一限制不能隐瞒。累计报告输入、输出、推理、
   失败和未知usage，规划估算与实际计费分开。
3. **新增问题与出口**：串组/共同反证按显式归属处理；坏JSON及缺组走原有限纠正；
   单组仍超容量保留具体未决并走原修订/人工处理；成功成果继续保存。企业资料缺失仍
   可生成留空稿，不把本次优化变成新的编制门禁，不把未完成核验伪装成通过。
4. **一次修订重跑量**：精确恢复为零新增成功调用；局部纠正按剩余目标计；共享依据
   改变时同批受影响组及下游重跑，最坏全分析。报告实际失效集，不能仅按修改段数估算。
5. **是否让模型誊写**：只返回必要短工作单元路由号、语义结论及证据/接受选择，不
   回抄来源清单、候选清单、metadata或已知覆盖。宿主按回执派生执行覆盖，不以此证明
   语义完整；完整性仍由独立核验和真实标注检查。

实施依次为：统一外层合同与回放用例 → associate共享输入及逐组保存 → joint与恢复 →
真实对照。第一批只在已有台账上测试少量有代表性的关联加joint，包含共同反证、空issue
补遗、独立问题及长输出；通过后完成同文件新运行。所有步骤使用同一预算和失败出口。

验收同时检查候选/原文无损、语义质量、完整associate+joint实际调用/Token/墙钟时间、
失败与修订放大；并发和模型保持可比。覆盖执行不能替代语义正确，输入下降不能替代耗时
下降。若joint重复或输出失败抵消收益，调整合批容量或暂用逐组，不追加多层Agent补救。
全流程还包括大纲、知识检索、写作、核对及导出，它们逐阶段单列成本，不能以分析提速
替代完整文件验收或承诺固定分钟数。
